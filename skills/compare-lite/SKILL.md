## Client workspace routing (mandatory for file changes)

Every generated file has exactly one home. Audit, keyword and comparison
outputs live under `work/{domain}/` created by `new-workspace-lite`
(`00-baseline/` first run, `01-current/` later runs, `02-fixes/`, `03-content/`,
`04-reports/`, `uploads/` read-only for user files); never invent another
top-level folder there. Content production and WordPress publishing use the
client workspace `clients/<client>/` created by `new-client-lite`: read
`workspace-routing.json` first, resolve every artifact with
`{PLUGIN_ROOT}/skills/rainmojo-so-lite/scripts/client_workspace.py route`, use the
most precise registered route, edit root files only when their exact filename is
in `root_policy.allowed_files`, treat `uploads/` as read-only, and when no route
fits use `create-work` then `route-work`; never construct a `work/<name>/...`
path by hand inside a client workspace. Never write generated files to the
plugin tree or the caller's working directory. Append one line to the
workspace's `CHANGELOG.md` or `log.md` after every write. Run
`client_workspace.py validate` before handing a client workspace over. Direct
CMS/API operations retain their own safety and verification gates.

## Presentation (Two-Tier, 7 modes)

Answer in the response mode that matches the request
(`{PLUGIN_ROOT}/skills/rainmojo-so-lite/_base/presentation-scaffold.md`): quick fact,
how-to, comparison, troubleshoot, audit, deployable, always closing with next
steps. A run that writes a deliverable ends with a Tier 1 card built from
`summary.json` (`templates/widget/summary.schema.json`) and rendered with
`{PLUGIN_ROOT}/skills/rainmojo-so-lite/scripts/present.py --target auto`, then hands
off to the Tier 2 file, which stays complete and unchanged. Lite cards carry
counts of checks passed, never a weighted score. Every card value is copied
from the deliverable; unmeasured values show as could not verify. No emoji on
any surface; the glyph allowlist applies to chat and Markdown only.

## ก่อนพูดว่าไม่มีอะไร ให้เปิดดูก่อนทุกครั้ง

**ห้ามประกาศว่าไฟล์หรือโฟลเดอร์ไม่มี ถ้ายังไม่ได้ไล่ดูรายชื่อจริง** ให้ไล่ดูทีละชั้น
คือดูว่ามีโฟลเดอร์ `work/{domain}/` ไหม แล้วในนั้นมีอะไรบ้าง แล้วค่อยเปิดแต่ละโฟลเดอร์ย่อย
การเขียนว่าไม่มีข้อมูลโดยไม่เปิดดู คือการมั่วชนิดเดียวกับการแต่งตัวเลข ต่างกันแค่มั่วเรื่องการไม่มีอยู่

เขียนเหตุผลที่เทียบไม่ได้ให้ตรงกับสิ่งที่เห็นจริง เช่น
รอบแรกมีผลตรวจสามหัวข้อ รอบล่าสุดยังไม่มีสักหัวข้อ จึงยังจับคู่ไม่ได้
ไม่ใช่เขียนว่าไม่มีไฟล์อะไรเลย ทั้งที่มีอยู่

**ข้อสรุปจากรายงานรอบก่อน ไม่ใช่สถานะปัจจุบัน** ถ้าจะยกข้อไหนมาเขียนซ้ำ
ให้เปิดไฟล์จริงที่ข้อนั้นพูดถึงก่อนทุกครั้ง โดยเฉพาะข้อที่รอบก่อนเขียนว่าตรวจไม่ได้หรือถูกบล็อก
เพราะไฟล์อาจถูกเก็บสำเร็จในภายหลังแล้ว การลอกข้อสรุปเก่ามาใช้เป็นสถานะวันนี้
ให้ผลผิดแบบเดียวกับการไม่เปิดดูเลย และมักจบด้วยการสั่งลูกค้าไปทำสิ่งที่ทำเสร็จแล้ว
ถ้าสองรายงานขัดกัน ให้เปิดไฟล์ตัดสิน แล้วเขียนว่ายึดอันไหนเพราะอะไร

**ห้ามสั่งให้ลูกค้าสร้างสิ่งที่มีอยู่แล้ว หรือส่งสิ่งที่อ่านได้เองจากพาธ**
ก่อนเขียนรายการสิ่งที่ต้องขอ ให้ตรวจก่อนว่าแต่ละข้อยังขาดจริง
ชื่อโดเมนอ่านได้จากชื่อโฟลเดอร์ ไม่ต้องถาม

**ห้ามอ้างชื่อไฟล์ภายในของสกิล เลขบรรทัด หรือ `agent.json` ในเอกสารที่ส่งลูกค้า**
ลูกค้าจ้างผลลัพธ์ ไม่ได้จ้างให้ดูเครื่องใน ถ้าจำเป็นต้องอธิบายว่าทำไมทำไม่ได้
ให้พูดด้วยภาษาของงาน เช่น ยังไม่มีผลตรวจรอบล่าสุด ไม่ใช่ชี้ไปที่บรรทัดในไฟล์สกิล
กฎนี้คลุมทุกไฟล์ที่เขียนลงในโฟลเดอร์งานของลูกค้า รวมถึงบันทึกการทำงานด้วย
ให้บันทึกเป็นชื่องาน เช่น เทียบผลสองรอบ ไม่ใช่ชื่อสกิลภายใน

## ข้อมูลที่ต้องมี

| ต้องมี | อยู่ที่ไหน |
|---|---|
| ผลรอบแรก | `work/{domain}/00-baseline/` |
| ผลรอบล่าสุด | `work/{domain}/01-current/` |
| บันทึกว่าระหว่างสองรอบทำอะไรไปบ้าง | `work/{domain}/CHANGELOG.md` |

**ถ้าไม่มี CHANGELOG ให้เตือนก่อน** เพราะจะเทียบได้แค่ว่าตัวเลขเปลี่ยน
แต่บอกไม่ได้ว่าเปลี่ยนเพราะอะไร ซึ่งเป็นคนละเรื่องกัน
**ไม่มี CHANGELOG ไม่ใช่เหตุผลให้ไม่ทำงาน** ให้เทียบต่อไป แล้วเขียนกำกับว่าสรุปสาเหตุไม่ได้

**ถ้าจับคู่หัวข้อไม่ได้เลยสักหัวข้อ ให้หยุด** แล้วบอกว่าต้องสแกนอีกรอบก่อน

**แต่ถ้าจับคู่ได้แม้แค่หัวข้อเดียว ต้องเทียบหัวข้อนั้นแล้วส่งงาน** อย่ารอให้ครบทุกหัวข้อ
หัวข้อที่มีข้อมูลรอบเดียวให้ลงกลุ่ม ไม่ได้วัด พร้อมบอกว่าขาดรอบไหน
**การอ้างว่าข้อมูลไม่ครบแล้วไม่ส่งงาน ไม่ใช่ความซื่อสัตย์** ส่วนที่เทียบได้ต้องส่ง
พร้อมติดป้ายให้ชัดว่าข้อไหนยืนยันแล้ว และข้อไหนต้องสแกนเพิ่มถึงจะยืนยันได้

## ขั้นที่ 1 จับคู่ไฟล์

จับคู่ไฟล์ด้วย **หัวข้อ** คือส่วนกลางของชื่อไฟล์ `{domain}_<หัวข้อ>_{วันที่}.md`
เช่น `crawler-access` ใน `00-baseline/` จับคู่กับ `crawler-access` ใน `01-current/` แม้วันที่ต่างกัน

**ถ้าหัวข้อเดียวกันมีหลายไฟล์ในโฟลเดอร์เดียว ให้ใช้ไฟล์ที่วันที่ในชื่อล่าสุด** แล้วระบุในรายงานว่าใช้ไฟล์ไหนเทียบกับไฟล์ไหน

ไฟล์ที่มีแค่ฝั่งเดียวให้แยกออกมารายงานต่างหาก เพราะแปลว่ารอบใดรอบหนึ่งไม่ได้สแกนหัวข้อนั้น
**ห้ามเอามาเทียบ** เพราะจะดูเหมือนเปลี่ยนแปลงทั้งที่แค่ไม่ได้วัด

### ขอบเขตของสองรอบต้องตรงกัน ไม่งั้นส่วนต่างใช้ไม่ได้

จับคู่ไฟล์ได้แล้ว ให้อ่านหัวรายงานของทั้งสองไฟล์ก่อนว่ารอบนั้นตรวจอะไรไปบ้าง กี่หน้า หน้าไหน

**ถ้าสองรอบตรวจคนละขอบเขต ส่วนต่างที่ได้ใช้ไม่ได้ ห้ามรายงานเป็นผลการเปลี่ยนแปลง**
เช่น รอบแรกตรวจ 5 หน้า รอบสองตรวจ 20 หน้า จำนวนปัญหาที่เพิ่มขึ้นมาจากการตรวจเยอะขึ้น
ไม่ได้มาจากเว็บแย่ลง ทางแก้มีทางเดียวคือ **คำนวณใหม่บนขอบเขตที่ตรงกัน**
คือตัดให้เหลือเฉพาะหน้าที่ตรวจทั้งสองรอบ แล้วเทียบเฉพาะชุดนั้น
ตัดแล้วเหลือน้อยเกินไปจนเทียบไม่ได้ ให้เขียนตรง ๆ ว่าเทียบไม่ได้เพราะขอบเขตไม่ตรงกัน
แล้วบอกว่าต้องสแกนหน้าชุดไหนเพิ่มถึงจะเทียบได้

ทุกครั้งที่ปรับขอบเขตให้ตรงกัน ต้องเขียนไว้ในรายงานว่าตัดอะไรออกไปบ้างและเหลือกี่หน้า

## ขั้นที่ 2 แบ่งผลเป็น 4 กลุ่ม

| กลุ่ม | หมายถึง | ทำอะไรต่อ |
|---|---|---|
| **แก้แล้วหาย** | รอบแรกเจอ รอบสองไม่เจอ | ยังไม่ใช่ข้อสรุปว่าวิธีที่ใช้ได้ผล ต้องผ่านสองด่านในขั้นที่ 3 ก่อน แล้วค่อยจดไว้ทำซ้ำ |
| **ยังอยู่** | เจอทั้งสองรอบ | ถ้าแก้ไปแล้วแต่ยังอยู่ แปลว่าแก้ไม่ตรงจุด |
| **เพิ่งโผล่** | รอบแรกไม่เจอ รอบสองเจอ | **กลุ่มนี้สำคัญที่สุด** ดูข้างล่าง |
| **ไม่ได้วัด** | มีข้อมูลแค่รอบเดียว หรือรอบใดรอบหนึ่งเขียนว่าตรวจไม่ได้ | ไปสแกนให้ครบก่อน อย่าเดา |

### ตรวจไม่ได้ ไม่เท่ากับ ไม่มี

ไฟล์รอบไหนเขียนว่าหัวข้อนั้น `ตรวจไม่ได้` **ห้ามนับเป็น แก้แล้วหาย และห้ามนับเป็น เพิ่งโผล่**
ให้ลงกลุ่ม **ไม่ได้วัด** แทน แล้วระบุว่ารอบไหนที่ตรวจไม่ได้ และขาดอะไร

ของที่ดึงข้อมูลไม่สำเร็จ กับของที่ไม่มีอยู่จริง เป็นคนละเรื่องกัน
สลับสองอย่างนี้เมื่อไร คนอ่านจะสรุปกลับด้าน เช่น คิดว่าแก้สำเร็จทั้งที่ยังไม่ได้แตะเลย

### กลุ่มเพิ่งโผล่ ต้องแยกให้ออกก่อนรายงาน

**อย่ารีบสรุปว่าเราทำพัง** ให้ถามสามข้อตามลำดับ

1. **เราแก้อะไรที่กระทบข้อนี้ไหม** ดูจาก CHANGELOG ถ้าใช่ นั่นคือสาเหตุที่เป็นไปได้มากที่สุด
   แต่ยังไม่ใช่ข้อสรุป ต้องผ่านสองด่านในขั้นที่ 3 ก่อนจะเขียนว่าเป็นเพราะสิ่งนั้น
2. **เว็บมีหน้าใหม่เพิ่มไหม** ถ้ามี ปัญหาอาจมาจากหน้าใหม่ ไม่ใช่จากที่เราแก้
3. **ถ้าไม่ใช่ทั้งสองข้อ** อาจเป็นฝั่งแพลตฟอร์มเปลี่ยนเอง หรือเป็น noise
   ให้เขียนว่า **ยังสรุปสาเหตุไม่ได้** แทนที่จะเดา

ตอบครบสามข้อแล้วยังไม่จบ ต้องไปไล่สองด่านในขั้นที่ 3 ต่อ ก่อนจะเขียนสาเหตุลงรายงาน

## ขั้นที่ 3 เรื่องความผันผวนที่ต้องพูดให้ชัด

**ตัวเลขที่ขยับไม่ได้แปลว่าเกิดจากสิ่งที่เราทำเสมอ**

สิ่งที่วัดจากฝั่ง AI เปลี่ยนได้เองแม้เราไม่แตะอะไรเลย เพราะค่ายเปลี่ยนโมเดลและวิธีค้นตลอด

| ประเภทข้อมูล | เชื่อได้แค่ไหน |
|---|---|
| robots.txt, llms.txt, schema, meta | **เชื่อได้สูง** เป็นสิ่งที่อยู่บนเว็บเรา เปลี่ยนเพราะเราแก้เท่านั้น |
| โครงเนื้อหาและ heading | เชื่อได้สูง |
| การถูกอ้างอิงโดย AI | **เชื่อได้ต่ำถ้าวัดแค่สองรอบ** ต้องวัดหลายรอบถึงจะเห็นแนวโน้ม |
| จำนวนคำค้นที่ AI ยิง | **ต่ำมาก** เปลี่ยนได้ทุกวันโดยเราไม่ได้ทำอะไร |

**เขียนระดับความเชื่อถือกำกับทุกข้อในรายงาน** ถ้าไม่เขียน คนอ่านจะคิดว่าทุกตัวเลขหนักแน่นเท่ากัน
ซึ่งจะพาไปตัดสินใจผิด

### ส่วนต่างคือการเคลื่อนไหวที่วัดได้ ไม่ใช่หลักฐานว่างานของเราทำให้เกิด

นี่คือกฎที่สำคัญที่สุดของสกิลนี้ **ส่วนต่างบอกได้แค่ว่าค่าขยับ ไม่ได้บอกว่าใครทำให้ขยับ**
ห้ามเขียนว่าดีขึ้นเพราะเราแก้ ถ้ายังไม่ได้ผ่านสองด่านข้างล่างนี้

**ด่านที่ 1 ทุกส่วนต่างต้องรายงานคู่กับสิ่งอื่นที่เปลี่ยนในช่วงเวลาเดียวกัน**
ห้ามรายงานส่วนต่างลอย ๆ โดยไม่มีบริบทนี้ ให้ไล่ถามผู้ใช้และจดไว้ทุกรอบ

| สิ่งที่ต้องถามหา | ตัวอย่าง |
|---|---|
| ฝั่งแพลตฟอร์มเปลี่ยนเอง | มีการอัปเดตอัลกอริทึมหรือเปลี่ยนโมเดลในช่วงนั้นไหม |
| ฤดูกาลของธุรกิจ | ช่วงนั้นเป็นโลว์ซีซันหรือไฮซีซันของสินค้านี้ไหม |
| คู่แข่งขยับ | มีคู่แข่งออกเนื้อหาใหม่ ลดราคา หรือทำแคมเปญใหญ่ไหม |
| ของที่ปล่อยขึ้นเว็บโดยไม่ใช่งานรอบนี้ | เว็บมีหน้าใหม่ เปลี่ยนธีม ย้ายโฮสต์ หรือทีมอื่นแก้อะไรไปไหม |

ไล่แล้วไม่รู้ ให้เขียนว่า **ยังไม่ทราบ** ห้ามเขียนว่าไม่มีอะไรเปลี่ยน เพราะสองอย่างนี้คนละความหมาย

**ด่านที่ 2 ติดป้ายว่า สรุปสาเหตุได้ เฉพาะเมื่อมีของเทียบที่ไม่ถูกแตะ**
คือมีกลุ่มควบคุม หรือมีชุดหน้าที่รอบนี้ไม่ได้แก้อะไรเลย แล้วชุดนั้นไม่ขยับไปทางเดียวกัน
ไม่มีของเทียบแบบนั้น ให้ติดป้ายว่า **สอดคล้องกับสิ่งที่เราทำ แต่ยังยืนยันสาเหตุไม่ได้**
คำว่าสอดคล้องกับคำว่าเป็นเพราะ เป็นคนละคำและห้ามใช้สลับกัน

### แย่ลงคือแย่ลง ห้ามแปลงเป็นโอกาส

**ค่าที่ตกลง ให้รายงานว่าตกลง** ห้ามเขียนใหม่ให้กลายเป็นโอกาส เป็นจุดที่รอพัฒนา
หรือเป็นผลดีในระยะยาว การกลบข้อนี้คือการโกหกลูกค้าด้วยถ้อยคำ
ให้ไล่สาเหตุที่เป็นไปได้แยกกันให้ชัด อย่าเอามาปนกัน

| สาเหตุที่เป็นไปได้ | ต้องทำอะไรเพิ่ม |
|---|---|
| ขอบเขตการตรวจกว้างขึ้น | คำนวณใหม่บนขอบเขตเดิมตามขั้นที่ 1 ก่อนสรุปอะไรทั้งสิ้น |
| เจอปัญหาใหม่ที่รอบแรกไม่ได้ตรวจ | ไล่รายการปัญหาใหม่ออกมา แล้วแยกออกจากของเดิม |
| ฝั่งแพลตฟอร์มเปลี่ยนหรือเป็นเรื่องฤดูกาล | ระบุช่วงเวลาและสิ่งที่เปลี่ยน |
| ถอยหลังจริงจากสิ่งที่เราแก้ | ระบุว่าสงสัยการแก้ตัวไหน และเสนอวิธีย้อนกลับ |

### ตัวเลขผลกระทบทางธุรกิจ เป็นค่าที่ประมาณจากแบบจำลอง

ถ้ารายงานมีตัวเลขทำนายผลทางธุรกิจ เช่น จะได้คนเข้าเว็บเพิ่มเท่าไร คิดเป็นมูลค่าเท่าไร
**ต้องเขียนกำกับว่าเป็นค่าประมาณจากแบบจำลอง ไม่ใช่ผลที่วัดได้จริง**
และต้องแยกออกมาคนละส่วนกับตัวเลขที่นับได้จริง ห้ามวางเรียงในตารางเดียวกันราวกับเป็นของชนิดเดียวกัน

## ขั้นที่ 4 ส่งออก

ไฟล์ `work/{domain}/04-reports/{domain}_compare_{YYYY-MM-DD}.md` โครงตามนี้

หัวตาราง รอบแรกวันที่ รอบล่าสุดวันที่ ห่างกันกี่วัน ขอบเขตที่ใช้เทียบว่าตรงกันหรือถูกตัดให้ตรง
และระหว่างนั้นทำอะไรไปบ้างสรุปจาก CHANGELOG

จากนั้นเรียงหัวข้อตามนี้

1. **สรุปหนึ่งย่อหน้า** ว่าโดยรวมดีขึ้นหรือไม่ และมั่นใจแค่ไหน
2. **สิ่งอื่นที่เปลี่ยนในช่วงเวลาเดียวกัน** ตามตารางในขั้นที่ 3 สี่แถว ฝั่งแพลตฟอร์ม ฤดูกาล คู่แข่ง
   และของที่ปล่อยขึ้นเว็บโดยไม่ใช่งานรอบนี้ ข้อไหนไม่รู้ให้เขียนว่า ยังไม่ทราบ
   หัวข้อนี้ต้องอยู่ก่อนตารางผลทุกครั้ง เพราะเป็นบริบทที่ใช้อ่านตารางที่เหลือ
3. **แก้แล้วหาย** ตารางมีคอลัมน์ เรื่อง / ทำอะไรไป / เชื่อถือได้แค่ไหน / สรุปสาเหตุได้หรือแค่สอดคล้อง
4. **ยังอยู่** ตารางมีคอลัมน์ เรื่อง / แก้ไปแล้วหรือยัง / ทำไมยังอยู่
5. **เพิ่งโผล่และแย่ลง** คือกลุ่มเพิ่งโผล่ในขั้นที่ 2 รวมกับข้อที่ผลถอยหลังจากรอบก่อน
   ตารางมีคอลัมน์ เรื่อง / สาเหตุที่เป็นไปได้ตามตารางในขั้นที่ 3 / มั่นใจแค่ไหน
   เขียนตรง ๆ ว่าแย่ลง ห้ามเปลี่ยนคำให้กลายเป็นโอกาส
6. **ไม่ได้วัด** ตารางมีคอลัมน์ เรื่อง / ขาดข้อมูลรอบไหน
7. **สิ่งที่ควรทำต่อ 5 ข้อ** เรียงตามผลกระทบ
8. **ข้อจำกัดของการเทียบครั้งนี้** เขียนตรง ๆ ว่าอะไรที่สรุปไม่ได้จากข้อมูลเท่าที่มี

## การ์ด Tier 1 ของสกิลนี้

จบงานทุกครั้งด้วยการ์ดสรุปตามชั้นแสดงผล (`so-present-lite`): โหมด `audit` `dimensions[].history` คือจำนวนข้อที่ผ่านของแต่ละด้านในรอบแรกถึงรอบล่าสุด เรียงเก่าไปใหม่ เพื่อให้การ์ดวาด sparkline, `key_risk` คือด้านที่ถอยหลังมากที่สุด, `actions` คือรายการที่ยังไม่ได้ทำจากข้อ 7, ห้ามใส่ `score.delta` เพราะรุ่นนี้ไม่มีคะแนน
ทุกค่าบนการ์ดคัดลอกจากไฟล์ผลลัพธ์ที่เพิ่งเขียน ห้ามประเมินเพิ่ม ข้อที่ตรวจไม่ได้ให้ขึ้นว่า ตรวจสอบไม่ได้
รุ่น Lite ไม่มีคะแนน จึงไม่ใส่บล็อก `score` ค่าใน `dimensions` คือจำนวนข้อที่ผ่านต่อจำนวนข้อที่ตรวจ
เรนเดอร์ด้วย `python {PLUGIN_ROOT}/skills/rainmojo-so-lite/scripts/present.py --summary <summary.json> --target auto --host {host}`
แล้วปิดด้วยบรรทัดส่งต่อไปยังไฟล์ผลลัพธ์ฉบับเต็ม ซึ่งต้องครบและไม่ถูกย่อ

## กฎ

- **ห้ามสรุปว่าดีขึ้นเพราะสิ่งที่เราทำ** ถ้า CHANGELOG ไม่มีบันทึกว่าทำอะไรที่เกี่ยวข้อง
- **ส่วนต่างคือการเคลื่อนไหวที่วัดได้ ไม่ใช่หลักฐานว่าเราทำให้เกิด**
  ห้ามรายงานส่วนต่างโดยไม่มีหัวข้อสิ่งอื่นที่เปลี่ยนในช่วงเดียวกันกำกับ
- **ห้ามติดป้ายว่าสรุปสาเหตุได้ ถ้าไม่มีของเทียบที่รอบนี้ไม่ได้แตะ** ให้เขียนว่าสอดคล้องแต่ยังยืนยันไม่ได้
- **ห้ามเทียบเมื่อสองรอบตรวจคนละขอบเขต** ให้คำนวณใหม่บนขอบเขตที่ตรงกันก่อน
  หรือเขียนว่าเทียบไม่ได้ ห้ามส่งส่วนต่างที่รู้อยู่แล้วว่าไม่ถูกต้อง
- **ห้ามเปลี่ยนคำว่าแย่ลงให้กลายเป็นโอกาส จุดที่รอพัฒนา หรือผลดีระยะยาว** ตกคือตก
- **ตัวเลขทำนายผลทางธุรกิจ ต้องเขียนกำกับว่าเป็นค่าประมาณจากแบบจำลอง**
  และห้ามวางในตารางเดียวกับตัวเลขที่นับได้จริง
- **ห้ามคิดเปอร์เซ็นต์การพัฒนาเป็นตัวเลขเดียว** เพราะรวมของที่เชื่อได้กับเชื่อไม่ได้เข้าด้วยกัน
- **ห้ามซ่อนกลุ่มเพิ่งโผล่** แม้จะทำให้รายงานดูไม่สวย เพราะนั่นคือส่วนที่มีค่าที่สุด
- **อ่านหรือดึงข้อมูลไม่สำเร็จ ให้เขียนว่า `ตรวจไม่ได้` ห้ามเขียนว่า `ไม่มี`**
- ถ้าข้อมูลไม่พอให้เขียนว่าไม่พอ แล้วส่งส่วนที่ทำได้ ห้ามใช้ข้อจำกัดเป็นเหตุผลไม่ส่งงาน
