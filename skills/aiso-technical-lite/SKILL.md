## ขั้นที่ 0 ดึง HTML ดิบและ response header มาเก็บไว้ก่อน

**ต้องเก็บ header ด้วย GET เท่านั้น ห้ามใช้ `curl -I` หรือ `-sSI`** เพราะบางเซิร์ฟเวอร์ตอบ
HEAD กับ GET ไม่เหมือนกัน เช่นส่ง `strict-transport-security` ให้เฉพาะ HEAD
ถ้าเก็บด้วย HEAD จะสรุปเรื่องความปลอดภัยและแคชกลับด้านจากที่ผู้ใช้จริงเจอ
ใช้ `-D` แนบกับการดึงหน้าปกติ ได้ทั้งไฟล์ HTML และ header จากคำขอเดียวกัน

**ต้องทำก่อนขั้นอื่นทั้งหมด** เพราะ WebFetch คืนเนื้อหาที่แปลงเป็นข้อความแล้ว
แท็กใน `<head>` อย่าง canonical, meta robots และ meta viewport ถูกตัดทิ้ง
และ WebFetch ไม่คืน response header ให้ดูเลย
ถ้าตรวจจากผล WebFetch อย่างเดียว จะรายงานว่า ไม่มี ทั้งที่มีอยู่ ซึ่งเป็นผลลบลวง

```bash
mkdir -p work/{domain}/uploads
curl -sSL -D work/{domain}/uploads/home-headers.txt \
  -A "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 Chrome/120" \
  -m 25 "https://{domain}/" -o work/{domain}/uploads/home.html
curl -sSL -A "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 Chrome/120" \
  -m 25 "https://{domain}/robots.txt" -o work/{domain}/uploads/robots.txt
```

ถ้าขอบเขตที่ประกาศไว้เป็นหลายหน้า ให้ทำแบบเดียวกันกับทุกหน้าตัวแทนแม่แบบ
ตั้งชื่อไฟล์ให้ต่างกัน แล้ว **ใช้ Grep กับไฟล์ที่ดาวน์โหลดมา** ไม่ใช่กับผล WebFetch

| หัวข้อที่ต้องดูจากไฟล์ดิบ | ดูที่ไหน |
|---|---|
| canonical, meta robots, viewport | `home.html` |
| mixed content `src="http://` และ `href="http://` | `home.html` |
| security header และ `x-robots-tag` | `home-headers.txt` |
| ทางเดินของ redirect และรหัสสถานะ | `home-headers.txt` |
| รายการบอทที่ถูกอนุญาตหรือถูกบล็อก | `robots.txt` |

### ถ้าใช้คำสั่งพวกนี้ไม่ได้

**บาง host ไม่มีเครื่องมือรันคำสั่งให้** เช่น Cowork, Claude Desktop และ GPT desktop
ถ้าเป็นแบบนั้น ให้ทำแบบนี้แทน แล้วงานจะยังเดินต่อได้

1. บอกผู้ใช้ว่า **ขอให้ช่วยเปิดหน้าเว็บแล้วคัดลอกซอร์สมาให้**
   วิธีคือเปิดหน้านั้นในเบราว์เซอร์ กด `Ctrl+U` หรือ `Cmd+Option+U` เพื่อดู source
   แล้วเลือกทั้งหมด คัดลอก มาวางในแชท
   ส่วน robots.txt ให้เปิด `https://{domain}/robots.txt` แล้วคัดลอกมาวางได้เลย
2. ถ้าผู้ใช้ทำให้ได้ ให้ทำงานต่อจากซอร์สที่ได้มา ตามขั้นตอนเดิมทุกอย่าง
3. **response header ดูจากซอร์สไม่ได้** ถ้าอยากได้ ให้ผู้ใช้เปิด DevTools แท็บ Network
   กดที่คำขอแรกแล้วคัดลอกส่วน Response Headers มาวาง
   ถ้าไม่สะดวก ให้เขียนกำกับหัวข้อที่ใช้ header ว่า `ตรวจไม่ได้`
4. ถ้าผู้ใช้ไม่สะดวกทั้งหมด ให้ใช้ WebFetch เท่าที่ได้ แล้ว**เขียนกำกับทุกหัวข้อที่กระทบว่า `ตรวจไม่ได้`**
   ห้ามเขียนว่า `ไม่มี` เพราะสองคำนี้คนละความหมาย และการเขียนผิดจะทำให้ผู้ใช้เข้าใจกลับด้าน

**บน Windows** ถ้ารันแล้วขึ้นว่าไม่รู้จักคำสั่ง ให้ลองใน Git Bash หรือ WSL
ถ้าไม่มีทั้งสองอย่าง ให้ใช้วิธีคัดลอกซอร์สในข้อ 1

## เนื้อหาที่ JavaScript สร้าง ต้องดูสามชั้น ไม่ใช่เทียบสองภาพ

การเทียบแค่ HTML ดิบกับหน้าที่เห็นบนจอ **แยกไม่ออก**ระหว่างเนื้อหาที่บอทซึ่งเรนเดอร์ได้จะเจอ
กับเนื้อหาที่ไม่มีบอทตัวไหนเจอเลย และสองอย่างนี้ **แก้คนละวิธีกันสิ้นเชิง**
ต้องเก็บภาพของ URL เดียวกันสามชั้น

| ชั้น | เก็บยังไง | แทนสายตาของใคร |
|---|---|---|
| **ชั้นที่ 1** HTML ดิบ ไม่รัน JS | ไฟล์ที่ดึงมาในขั้นที่ 0 | บอทที่ไม่เรนเดอร์ ได้เท่านี้เป๊ะ ๆ |
| **ชั้นที่ 2** DOM หลัง JS ทำงานเสร็จ ยังไม่แตะหน้า | เปิดในเบราว์เซอร์ เปิด DevTools แท็บ Elements คลิกขวาที่ `<html>` แล้ว Copy outerHTML **โดยยังไม่กดอะไรบนหน้า** | บอทที่เรนเดอร์ได้ ในการเดินหนึ่งรอบ |
| **ชั้นที่ 3** DOM หลังไปกดอะไรบนหน้า | จากชั้นที่ 2 ให้กดแท็บ กางแอคคอร์เดียน กดโหลดเพิ่ม แล้ว Copy outerHTML อีกรอบ | คนที่นั่งดูอยู่ · **ไม่มีบอทตัวไหนไปถึงชั้นนี้** |

**ชั้นที่ 2 กับ 3 เก็บด้วย `curl` หรือ WebFetch ไม่ได้** ต้องขอให้ผู้ใช้เปิดเบราว์เซอร์เก็บมาให้ตามตาราง
ผู้ใช้ทำให้ไม่ได้ ก็ให้ทำเท่าที่มี แล้ว **ลงว่า `ตรวจไม่ได้` สำหรับข้อที่ต้องใช้สองชั้นนั้น ห้ามลงว่า ไม่มี**

**ซอร์สที่กด `Ctrl+U` มาได้ นับเป็นชั้นที่ 1 เท่านั้น** ห้ามเอาไปตอบคำถามของชั้นที่ 2 หรือชั้นที่ 3
เพราะมันแสดงตัวสคริปต์ ไม่ได้แสดงผลลัพธ์หลังเรนเดอร์

**สิ่งที่ต้องเอามาเทียบทีละชั้น** เนื้อความหลัก หัวข้อ ลิงก์ในเมนูและในเนื้อหา บล็อก structured data
และ title / meta description / canonical

**ชั้นที่หายไป เป็นตัวบอกว่าต้องแก้อะไร**

| หายไปตรงไหน | แปลว่า | ตระกูลของทางแก้ |
|---|---|---|
| มีในชั้นที่ 2 แต่ไม่มีในชั้นที่ 1 | บอทที่ไม่เรนเดอร์มองไม่เห็น | เรื่องวิธีเรนเดอร์ ย้ายเนื้อหาไปอยู่ในคำตอบจากเซิร์ฟเวอร์ |
| มีในชั้นที่ 3 แต่ไม่มีในชั้นที่ 2 | **บอททุกตัวมองไม่เห็น ไม่ว่าจะเรนเดอร์ได้หรือไม่** เพราะไม่มีบอทตัวไหนกดอะไร | เรื่องโครงลิงก์ ต้องมี URL ของตัวเอง หรือมีเส้นลิงก์ที่บอทเดินไปถึงได้ · การไปแก้วิธีเรนเดอร์ไม่ช่วยอะไรกับข้อนี้เลย |

**ต้องบันทึกว่าของที่หายไปแต่ละชิ้นอยู่ชั้นไหน** รายงานที่เขียนแค่ว่า ไม่มีใน HTML ดิบ
คือการยุบข้อบกพร่องสองแบบเป็นแบบเดียว แล้วจะได้ทางแก้ผิดอย่างน้อยหนึ่งอัน

### เนื้อหาที่ต้องกดถึงจะเห็น เป็นข้อค้นพบของตัวเอง ไม่ใช่ปัญหาการเรนเดอร์

สเปกที่ซ่อนในแท็บ, FAQ แบบแอคคอร์เดียน, รายการที่ต้องกดโหลดเพิ่ม, เนื้อหาที่โผล่ตอนเอาเมาส์ไปชี้
และอะไรก็ตามที่อยู่หลังการกดส่งฟอร์ม **หายไปจากการเก็บข้อมูลของบอทหมด แม้บอทตัวนั้นเรนเดอร์ได้เต็มที่**

วิธีวินิจฉัยคือเอาชั้นที่ 2 เทียบกับชั้นที่ 3 แล้วไล่รายการทุกอย่างที่มีเฉพาะในชั้นที่ 3 **รายการนั้นคือข้อค้นพบ**
แต่ละบล็อกต้องได้อย่างใดอย่างหนึ่ง คือ URL ของตัวเอง หรือเส้นลิงก์ที่บอทเดินไปถึงได้
ใช้กฎเดียวกันกับสถานะที่สลับกันอยู่บน URL เดียว เพราะมีแค่สถานะตั้งต้นที่ถูกเก็บเข้าดัชนี

**ตรงกันข้าม การจงใจเอาการผสมตัวกรองและการจัดเรียงไปไว้หลังการกด เป็นวิธีที่ถูกต้อง**
เจอแบบนั้นให้บันทึกว่าเป็นการเลือกที่ตั้งใจและถูกแล้ว **ห้ามลงเป็นข้อบกพร่อง**

### ลิงก์ที่บอทเดินไม่ได้ เป็นเรื่องโครงลิงก์ ไม่ใช่เรื่องการเรนเดอร์

**ลงสองอย่างนี้ไว้ในหมวดโครงลิงก์เสมอ ห้ามลงในหมวดการเรนเดอร์** เพราะทางแก้คือแก้ markup ไม่ใช่แก้วิธีเรนเดอร์
ลงผิดหมวดคือส่งลูกค้าไปแก้ผิดที่

| แบบ | รายละเอียด | ทางแก้ |
|---|---|---|
| เมนูที่ไม่ได้ทำด้วยแท็ก `<a>` | ใช้แท็กอื่นแล้วแปะ script ไว้ตอนคลิกแทนการมี `href` | ใช้ `<a href>` จริงที่ชี้ไป URL ปลายทาง จะแปะ script ทับไว้ด้วยก็ได้ |
| URL ที่ต่างกันแค่ตรงหลัง `#` | ทุกปลายทางใช้ URL เดียวกัน ต่างกันแค่ fragment | ให้แต่ละปลายทางมี path ของตัวเองที่ยืนอยู่ได้เอง |

ทั้งสองแบบ framework อนุญาตให้ทำ และทั้งสองแบบให้ผลเป็น **โครงลิงก์ที่บอทเดินได้เป็นศูนย์**
ถึงหน้าจะเรนเดอร์ออกมาสวยงามก็ตาม หน้าที่อยู่หลังลิงก์พวกนี้จึงไม่มีใครค้นพบ
**ชั้นที่ 1 กับชั้นที่ 2 ตรงกันดี ไม่ได้แปลว่าเว็บนี้ปลอดข้อบกพร่องนี้**

### เส้นแบ่งของ cloaking และกันการกล่าวหาผิด

**การเรนเดอร์ฝั่งผู้ใช้ ไม่ใช่ cloaking** การส่งเวอร์ชันที่เรนเดอร์จากเซิร์ฟเวอร์ให้บอท
และส่งเวอร์ชันที่เรนเดอร์ฝั่งผู้ใช้ให้คน **ยอมรับได้** ตราบใดที่เนื้อหาสองฝั่งเป็นเรื่องเดียวกันจริง

สี่อย่างนี้เป็น cloaking เสมอ ไม่ว่าจะอ้างเจตนาอะไร

1. เนื้อหาที่ซ่อนด้วย `display:none` โดยตั้งใจทำไว้ป้อนเครื่องมือค้นหาโดยเฉพาะ
2. เนื้อหาที่มีอยู่แต่ใน `<noscript>` เท่านั้น
3. ข้อความที่อบไว้ในรูปภาพ
4. เนื้อหาที่ถูกสลับตาม IP หรือตามชื่อ user agent

**แต่ความต่างที่เกิดขึ้นเองตามธรรมชาติจากการเรนเดอร์ฝั่งผู้ใช้ ตามปกติแล้วไม่ใช่ cloaking**
ให้ลงเป็น **ความเสี่ยงว่าเนื้อหาพึ่งการเรนเดอร์** ห้ามลงเป็นการละเมิด cloaking
ยกระดับเป็น cloaking ได้กรณีเดียวคือความต่างนั้นเกิดที่ฝั่งเซิร์ฟเวอร์ **และ** ขึ้นกับว่าใครเป็นคนขอหน้ามา

**ข้อนี้มีไว้กันความผิดพลาดที่ร้ายแรงมาก** ถ้าไม่มีข้อนี้ การเจอว่า HTML ต้นทางไม่เหมือนหน้าที่เรนเดอร์แล้ว
จะทำให้เว็บ single-page application ธรรมดา ๆ ถูกยกระดับเป็นการกล่าวหาว่าลูกค้าทำ cloaking ในรายงาน
ซึ่งเป็นข้อกล่าวหาที่หนักและผิด

### หน้าที่ต้องรอเรนเดอร์ ขึ้นดัชนีช้ากว่า

หน้าที่ต้องผ่านการเรนเดอร์ก่อนจะเข้าคิวรอ ส่วนหน้าที่เซิร์ฟเวอร์เรนเดอร์มาให้เสร็จแล้วข้ามคิวนั้นไปเลย
นี่จึงไม่ใช่แค่เรื่องมองเห็นหรือไม่เห็น แต่เป็นเรื่องว่า **ข้อมูลขึ้นดัชนีช้าแค่ไหน**

ข้อมูลที่ความถูกต้องขึ้นกับเวลา คือ **ราคา ของมีหรือหมด วันจัดงาน และเนื้อหาข่าวด่วน
ต้องอยู่ใน HTML ที่เซิร์ฟเวอร์ส่งมา** และต้องบอกลูกค้าที่ใช้การเรนเดอร์ฝั่งผู้ใช้ตรง ๆ ว่า
เนื้อหาใหม่และเนื้อหาที่แก้แล้วจะขึ้นดัชนีช้ากว่า โดยเป็นความช้าที่ตัวเองคุมไม่ได้
**ห้ามระบุเป็นตัวเลขวินาทีหรือนาที** ถ้าไม่ได้วัดเอง

## ถ้อยคำที่ตรวจสอบข้อเท็จจริงแล้ว (ใช้ตามนี้ ห้ามเขียนกลับด้าน)

- **Googlebot รัน JavaScript ได้** และเรนเดอร์หน้าก่อนจัดดัชนี สิ่งที่รอเรนเดอร์จึงขึ้นดัชนีช้ากว่า ไม่ใช่ขึ้นไม่ได้
  ส่วนบอทค้นหาของ AI ส่วนใหญ่ (OAI-SearchBot, ChatGPT-User, PerplexityBot, Claude-SearchBot) **ไม่รัน JavaScript**
  ข้อความที่มีเฉพาะหลังสคริปต์ทำงานจึงมองไม่เห็นสำหรับบอทกลุ่มนี้ รายงานต้องแยกสองกลุ่มนี้ให้ชัด
- **Core Web Vitals เป็นเรื่องผู้ใช้และ Google** ไม่ใช่สิ่งที่ AI agent รอ INP ไม่ใช่ตัวเลขที่ agent ใช้ตัดสินใจเลิกทำงาน
  agent มีงบเวลาต่อขั้นเป็นวินาทีถึงนาที และสังเกตหน้าซ้ำหลังลงมือทำ สิ่งที่สำคัญคือ DOM นิ่งในช่วงนั้นและข้อความยืนยันยังอยู่
- **การไม่มี aria-live ไม่ทำให้ agent ค้าง** agent ไม่ฟังเหตุการณ์ live region แต่กลับมาอ่านหน้าใหม่เอง
  live region ยังควรมีเพื่อให้ role ของข้อความอยู่ใน accessibility tree และเพื่อผู้ใช้ screen reader
- **agent รับรู้หน้าเว็บ 3 แบบ** (ตรวจสอบกับเอกสารผู้ผลิต 2026-09) คือ accessibility tree (Playwright MCP, Claude in Chrome,
  Perplexity Comet, ChatGPT Atlas), DOM บวกภาพหน้าจอ (Browser Use, Project Mariner) และภาพหน้าจออย่างเดียว
  (OpenAI Operator, Anthropic computer use, Gemini Computer Use) HTML เชิงความหมายจึงตัดสินว่าสองกลุ่มแรกเห็นอะไร
  รายละเอียดการตรวจอยู่ใน `aiso-agent-readiness-lite` สกิลนี้อ้างผลจากที่นั่น ไม่วัดซ้ำ
- **การเข้าถึงได้ (accessibility) ไม่ใช่ปัจจัยจัดอันดับของ Google** อ้างได้แค่ว่ากระทบผู้ใช้และ AI agent
  ห้ามเขียนว่าแก้ accessibility แล้วอันดับจะดีขึ้น

## URL ซ้ำ บันไดวิธีแก้ ห้ามสลับขั้น

สี่วิธีนี้ **เรียงลำดับไว้ ไม่ใช่ตัวเลือกที่เท่ากัน** ให้ไล่จากขั้นที่ 1 ลงมา
และลงมาขั้นถัดไปได้ต่อเมื่อขั้นบนทำไม่ได้จริง ๆ กับลูกค้ารายนี้
**รายงานที่ลิสต์สี่ข้อนี้เป็นตัวเลือกที่มีศักดิ์เท่ากัน คือรายงานที่ผิด**

1. **กำจัด URL ซ้ำที่ต้นทาง ดีที่สุด** ให้เหลือ URL เดียวที่ให้บริการเนื้อหานั้น
   แล้ว 301 จาก URL ที่เลิกใช้ทุกตัวมาที่ตัวที่เหลือ **การ 301 คือสิ่งเดียวที่ยกน้ำหนักที่แต่ละ URL สะสมไว้มาให้ตัวที่เหลือ**
   ไม่มีขั้นไหนข้างล่างทำแบบนี้ได้ · ต้นทุนคือต้องไปแก้ที่ต้นเหตุของการซ้ำ ไม่ใช่แค่แปะแท็ก
2. **canonical** เป็นแค่ข้อเสนอแนะ เครื่องมือค้นหาจะไม่ทำตามก็ได้
   แต่สิ่งที่ได้กลับมาคือ URL ซ้ำยังเปิดเข้าได้ และยังวัดแยกกันได้ใน analytics ต่างจาก 301 ที่ย้ายคนไปด้วย
   นี่คือเหตุผลที่เลือกขั้นนี้เมื่อขั้นที่ 1 ทำไม่ได้
3. **noindex ระดับหน้า**
4. **ปิดใน robots.txt อยู่ท้ายสุดสำหรับกรณี URL ซ้ำโดยเฉพาะ** ด้วยสามเหตุผล คือ
   URL ซ้ำที่ไม่ถูกเก็บก็ยังกินโควตาการค้นพบอยู่ดี, ลิงก์ที่ชี้มาที่มันยังค้างเติ่งอยู่ที่เดิม,
   และสัญญาณของมันยุบรวมเข้ากับตัวที่เหลือไม่ได้เลย

**ต้องเขียนลำดับนี้ลงในรายงานทุกครั้งที่จะเสนอให้ปิดใน robots.txt หรือทุกครั้งที่เจอว่าปิดไว้อยู่แล้ว**
เพราะการปิดใน robots.txt เป็นทางที่ง่ายที่สุด จึงเป็นทางที่คนคว้าก่อนเสมอ

**การหาว่า URL ไหนซ้ำกับ URL ไหน** เป็นงานของ `technical-audit-lite`
ส่วน **ไฟล์ robots.txt ที่จะเอาไปวางจริง** เป็นงานของ `aiso-crawlers-lite`

## กฎ

- **ดึงข้อมูลไม่สำเร็จให้เขียนว่า `ตรวจไม่ได้` ห้ามเขียนว่า `ไม่มี` และห้ามเขียนว่า `ผ่าน`**
  ไม่มี แปลว่าเห็นซอร์สหรือ header แล้วและไม่พบ ตรวจไม่ได้ แปลว่ายังไม่ได้เห็น
  สองคำนี้คนละความหมาย เขียนผิดจะทำให้ผู้ใช้สรุปกลับด้าน
  ทุกช่องที่เขียนว่าตรวจไม่ได้ ต้องบอกด้วยว่าขาดอะไรถึงจะตรวจได้
- **ข้อที่ตรวจไม่ได้ ห้ามนับเป็นข้อที่ผ่านและห้ามนับเป็นข้อที่ตก** ให้แยกออกมาเป็นรายการต่างหาก
- **ทำได้แค่ไหนให้ส่งแค่นั้น ห้ามส่งงานเปล่าและห้ามปฏิเสธทั้งงาน**
  ตรวจได้บางหมวดหรือบางหน้า ให้ส่งส่วนที่ตรวจได้เสมอ
  พร้อมติดป้ายทุกบรรทัดว่า ยืนยันแล้ว หรือ ต้องยืนยันเพิ่ม
  แล้วแยกรายการที่ยังตรวจไม่ได้ไว้ท้ายรายงานพร้อมบอกว่าต้องใช้อะไรเพิ่ม
  **การอ้างข้อจำกัดเพื่อไม่ส่งงาน ไม่ใช่ความซื่อสัตย์**
- **ห้ามเขียนว่าเว็บทำ cloaking เพียงเพราะ HTML ต้นทางไม่เหมือนหน้าที่เรนเดอร์แล้ว**
  นั่นคืออาการปกติของการเรนเดอร์ฝั่งผู้ใช้ ให้ลงเป็นความเสี่ยงว่าเนื้อหาพึ่งการเรนเดอร์
  ยกระดับเป็น cloaking ได้เมื่อความต่างเกิดที่ฝั่งเซิร์ฟเวอร์และขึ้นกับว่าใครขอหน้ามาเท่านั้น
- **ของที่หายไป ต้องบอกว่าหายตั้งแต่ชั้นไหน** ห้ามเขียนแค่ว่าไม่มีใน HTML ดิบ
  เพราะจะยุบข้อบกพร่องสองแบบที่แก้คนละวิธีเข้าด้วยกัน
- **เสนอวิธีแก้ URL ซ้ำ ต้องเรียงตามบันไดสี่ขั้น** ห้ามเสนอการปิดใน robots.txt
  โดยไม่บอกว่ามันอยู่ขั้นล่างสุดและเพราะอะไร

## การ์ด Tier 1 ของสกิลนี้

จบงานทุกครั้งด้วยการ์ดสรุปตามชั้นแสดงผล (`so-present-lite`): โหมด `audit` `dimensions` คือจำนวนข้อที่ผ่านต่อจำนวนข้อที่ตรวจได้ในแต่ละหมวด (ผลจาก `page_analyzer.py --output json` ผ่าน `build_summary.py --page` สำหรับหมวด SSR, การเข้าถึงบอท, บล็อกเนื้อหา, llms.txt), `key_risk` คือข้อที่กั้นการเข้าถึงมากที่สุด, `actions` ไม่เกิน 4 ข้อ, `transparency.could_not_verify` คือชั้นที่ 2 และ 3 เมื่อผู้ใช้เก็บมาให้ไม่ได้
ทุกค่าบนการ์ดคัดลอกจากไฟล์ผลลัพธ์ที่เพิ่งเขียน ห้ามประเมินเพิ่ม ข้อที่ตรวจไม่ได้ให้ขึ้นว่า ตรวจสอบไม่ได้
รุ่น Lite ไม่มีคะแนน จึงไม่ใส่บล็อก `score` ค่าใน `dimensions` คือจำนวนข้อที่ผ่านต่อจำนวนข้อที่ตรวจ
เรนเดอร์ด้วย `python {PLUGIN_ROOT}/skills/rainmojo-so-lite/scripts/present.py --summary <summary.json> --target auto --host {host}`
แล้วปิดด้วยบรรทัดส่งต่อไปยังไฟล์ผลลัพธ์ฉบับเต็ม ซึ่งต้องครบและไม่ถูกย่อ

## การวางไฟล์ผลลัพธ์

สกิลนี้อยู่ในชุดที่ใช้โครงโฟลเดอร์ของสกิล `new-workspace-lite`

1. ผลลัพธ์ทุกไฟล์อยู่ใต้ `work/{domain}/`
2. ถ้า `work/{domain}/00-baseline/` ยังไม่มีไฟล์หัวข้อเดียวกัน ให้เขียนลง `00-baseline/` ถ้ามีแล้ว ให้เขียนลง `01-current/`
3. เขียนเสร็จ ให้เพิ่มบรรทัดลงตารางใน `work/{domain}/CHANGELOG.md` ว่าวันที่ รันสกิลอะไร ได้ไฟล์อะไร
4. ถ้ายังไม่มี `work/{domain}/` ให้แนะนำผู้ใช้รันสกิล `new-workspace-lite` ก่อน ห้ามสร้างโครงเองแบบอื่น

## สคริปต์ที่ให้มาด้วย

```bash
python {PLUGIN_ROOT}/skills/rainmojo-so-lite/scripts/page_analyzer.py https://{domain}/ --output json
```

ให้ 4 ข้อตรวจ (SSR-01 ข้อความหลักอยู่ใน HTML ดิบ, BOT-01 บอทค้นหาที่มีเอกสารเข้าได้, CNT-01 บล็อกที่อยู่ได้ด้วยตัวเอง, LLM-01 llms.txt)
แต่ละข้อเป็น PASS, FAIL, INFO หรือ COULD NOT VERIFY อ่าน robots.txt ตาม RFC 9309 ไม่มีคะแนนและไม่มีน้ำหนัก
ผลของสคริปต์เป็นชั้นที่ 1 เท่านั้น ไม่แทนชั้นที่ 2 และ 3
