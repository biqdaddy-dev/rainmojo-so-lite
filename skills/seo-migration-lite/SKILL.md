## Client workspace routing (mandatory for file changes)

Every generated file has exactly one home. Audit, keyword and comparison
outputs live under `work/{domain}/` created by `new-workspace-lite`
(`00-baseline/` first run, `01-current/` later runs, `02-fixes/`, `03-content/`,
`04-reports/`, `uploads/` read-only for user files); never invent another
top-level folder there. Content production and WordPress publishing use the
client workspace `clients/<client>/` created by `new-client-lite`: read
`workspace-routing.json` first, resolve every artifact with
`{PLUGIN_ROOT}/skills/rainmojo-so-lite/scripts/client_workspace.py route`, use the
most precise registered route, edit root files only when their exact filename is
in `root_policy.allowed_files`, treat `uploads/` as read-only, and when no route
fits use `create-work` then `route-work`; never construct a `work/<name>/...`
path by hand inside a client workspace. Never write generated files to the
plugin tree or the caller's working directory. Append one line to the
workspace's `CHANGELOG.md` or `log.md` after every write. Run
`client_workspace.py validate` before handing a client workspace over. Direct
CMS/API operations retain their own safety and verification gates.

# วางแผนย้ายเว็บ

การย้ายเว็บคือการเปลี่ยน URL โดเมน โฮสต์ หรือแพลตฟอร์ม ทุกแบบมีความเสี่ยงเดียวกันคือ
**ลิงก์และอันดับที่สะสมมาชี้ไปยังที่อยู่ที่เลิกตอบแล้ว** และมีเครื่องมือคุมเดียวกันคือ
**ตาราง redirect ที่ครบและใช้งานได้จริงตั้งแต่นาทีแรกที่สลับของ**

แยกประเภทการย้ายก่อนเสมอ เพราะประเภทซ้อนกันได้ เช่นย้ายแพลตฟอร์มพร้อมเปลี่ยนโดเมน ต้องทำสองชุด

| ประเภท | path เปลี่ยนไหม | โดเมนเปลี่ยนไหม | เซิร์ฟเวอร์เปลี่ยนไหม | ต้องทำอะไร |
|---|---|---|---|---|
| เปลี่ยนโครง URL หรือรีดีไซน์ | เปลี่ยน | ไม่ | อาจเปลี่ยน | ตาราง URL |
| เปลี่ยนหรือรวมโดเมน | อาจเปลี่ยน | เปลี่ยน | อาจเปลี่ยน | ตาราง URL + ลำดับเปลี่ยนโดเมน + ด่านตรวจโดเมนต้นทาง |
| ย้ายโฮสต์หรือเซิร์ฟเวอร์ | ไม่ | ไม่ | เปลี่ยน | checklist ย้ายโฮสต์ |
| เปลี่ยนแพลตฟอร์มหรือ CMS | ส่วนใหญ่เปลี่ยน | ไม่ | ส่วนใหญ่เปลี่ยน | ตาราง URL + checklist ย้ายโฮสต์ |

ถ้า URL ไม่เปลี่ยนเลย คือย้ายโฮสต์อย่างเดียว ให้ข้ามตาราง URL ได้ แต่ **checklist ย้ายโฮสต์ยังต้องทำครบทุกข้อ**

## ขั้นที่ 1 ทำตาราง URL เก่าไปใหม่

ตารางนี้คือตัวงานย้ายเว็บ **ต้องทำให้เสร็จก่อนตกลงวันขึ้นระบบ** ไม่ใช่ทำหลังจากนั้น

1. **รวบรวม URL จากหลายแหล่งแล้วค่อยตัดซ้ำ** ไม่มีแหล่งไหนเห็นเว็บทั้งเว็บ
   ให้ดึงจาก server log, sitemap ปัจจุบัน, การ crawl รอบใหม่, เครื่องมือดู backlink และรายการหน้าที่ถูกเก็บดัชนี
   แล้วนำมารวมและตัดซ้ำ **URL ที่โผล่เฉพาะใน log หรือในข้อมูล backlink
   คือกลุ่มที่การ crawl อย่างเดียวจะทำหล่นไปเงียบ ๆ**
2. **แถวมีสองแบบ** แบบรายตัว หนึ่ง URL เก่าต่อหนึ่ง URL ใหม่ ใช้กับหน้าสำคัญหรือหน้าที่ไม่เข้ารูปแบบ
   และแบบ pattern ใช้กับหมวดที่แปลงตามกฎได้
   ทุก URL ในรายการต้องตกลงในแถวใดแถวหนึ่งพอดี **ต้องเอา pattern ไปทดสอบกับรายการเต็มก่อนเชื่อ**
3. **ใส่ไฟล์ที่ไม่ใช่ HTML ด้วย** รูป PDF ไฟล์ดาวน์โหลด และ feed
   ของพวกนี้มีลิงก์และมีอันดับเหมือนกัน และเป็นกลุ่มที่ถูกลืมบ่อยที่สุด
4. **หน้าที่จะเลิกใช้ต้องระบุปลายทางชัดเจน** หน้าที่ไม่มีของใหม่มาแทน ให้ redirect ไปหน้าที่ใกล้เคียงที่สุด
   ถ้าไม่มีจริง ๆ ให้ไปหน้าหมวดแม่ **ห้ามโยนทุกหน้าที่เลิกใช้ไปหน้าแรก
   และห้ามปล่อยให้ 404 เพราะลืมใส่ในตาราง** ตารางต้องตัดสินให้ครบทุกแถว
5. **เรียงความสำคัญตามลิงก์** URL ที่มีลิงก์เข้าจริงเท่านั้นที่คุ้มกับการทำแถวรายตัว
   ที่เหลือให้ไปกับ pattern หรือปล่อยเลิกใช้ **ลงแรงมือทำตรงที่มีของสะสมอยู่**

**เงื่อนไขหยุด** ถ้าแหล่งข้อมูลขัดกันมากจนคุมไม่อยู่ หรือทำตารางให้ครอบคลุมรายการทั้งหมดไม่ได้
**ให้เลื่อนวันขึ้นระบบ** ตารางที่ไม่ครบตอนสลับของ คือความเสียหายก้อนใหญ่ที่สุดที่ทำใส่ตัวเองได้ในงานย้ายเว็บ

## ขั้นที่ 2 ลำดับขั้นเปลี่ยนโดเมน

**ลำดับสำคัญกว่าความเร็ว** ทำตามนี้

1. **จดและวางของบนโดเมนใหม่ล่วงหน้า** ให้มีหน้าที่ crawl ได้อยู่ก่อนวันย้ายพอสมควร
   บอทจะได้รู้จักโดเมนนี้อยู่แล้วตอนสลับของ
2. **ถ้าเป็นโดเมนเก่าที่ไปเอามา ต้องตรวจประวัติก่อนรับมาใช้** ดูด่านตรวจในขั้นที่ 3
   ข้อนี้ใช้กับทุกโดเมนที่ไม่ได้จดใหม่เอง
3. **ยืนยันสิทธิ์ทั้งสองโดเมนใน Search Console ก่อนวันย้าย** ทั้งของเก่าและของใหม่
   เพื่อให้แจ้งย้ายที่อยู่และเฝ้าดูผลได้ตั้งแต่วันแรก
4. **redirect ต้องครบทั้งชุดตั้งแต่วันขึ้นระบบ** ไม่ใช่ทยอยใส่ทีหลัง ไม่ใช่ทำหน้าสำคัญก่อน
   ตารางทั้งตารางต้องตอบได้ตั้งแต่นาทีแรกที่โดเมนใหม่เป็นตัวหลัก
5. **แจ้งเปลี่ยนที่อยู่ใน Search Console หลังยืนยันแล้วว่า redirect ทำงานจริง** ไม่ใช่ก่อน
6. **ติดต่อเว็บที่ลิงก์มาหาเราให้แก้ลิงก์เป็นโดเมนใหม่**
   **ให้เริ่มจากเว็บที่ส่ง traffic มาให้เรามากที่สุดก่อน แล้วไล่ลงไปตามลำดับ**
   redirect รักษาของไว้ได้เกือบหมด แต่ลิงก์ที่ถูกแก้จริงรักษาได้ดีกว่า
   และยังอยู่ต่อแม้วันหนึ่งจะเลิกทำชั้น redirect
7. **รวมโดเมนทีละโดเมน ห้ามรวมรวดเดียวหลายโดเมน** ถ้าโดเมนไหนมีปัญหาจะได้ยังหาเจอ
   ไม่ใช่เกลี่ยปัญหาปนกันทั้งก้อน

## ขั้นที่ 3 ด่านตรวจโดเมนต้นทาง

**ก่อนรวมหรือรับโดเมนเดิมของใครมาใช้ ต้องตรวจว่าโดเมนนั้นติดโทษอยู่หรือเปล่า
เพราะ redirect ดึงบทลงโทษตามมาพร้อมกับของดี**

- **สิ่งที่ต้องดู** สถานะ Manual actions ใน Search Console ของโดเมนต้นทาง ถ้าเจ้าของเดิมเปิดให้ดูได้
  ถ้าเข้าไม่ได้ ให้ดูร่องรอยเท่าที่เห็นจากภายนอก เช่นเนื้อหาเก่าที่ยังค้างอยู่ในผลค้น
  ประวัติการใช้งานของโดเมน และหน้าตาของลิงก์ที่ชี้เข้ามา
  โปรไฟล์ลิงก์ให้ประเมินด้วย `seo-backlink-strategy-lite`
- **ผ่านด่าน** ไม่มี manual action และไม่เห็นสัญญาณผิดปกติ ให้เดินตามลำดับในขั้นที่ 2 ต่อได้
- **ไม่ผ่านด่าน** **ห้าม redirect** งานย้ายของโดเมนนั้นให้หยุดไว้ก่อนจนกว่าจะเคลียร์เรื่องลิงก์และโทษเสร็จ
- **ตรวจไม่ได้** ให้เขียนว่า `ตรวจไม่ได้` และบอกว่าขาดอะไร **ห้ามเขียนว่าผ่าน**

## ขั้นที่ 4 checklist ย้ายโฮสต์หรือเซิร์ฟเวอร์

ทำตามลำดับ ทุกข้อมาจากอาการพังที่เจอจริง

1. **ตรวจว่าโฮสต์ใหม่มี runtime และโมดูลครบ** ทั้งตัวรันภาษา ส่วนขยาย และโมดูล rewrite ที่เว็บใช้
   ต้องยืนยันให้ครบก่อนชี้อะไรไปที่เครื่องใหม่
2. **ไฟล์ที่ไม่ใช่เนื้อหาและมักถูกลืม** ไฟล์ robots, ไฟล์ตั้งค่า rewrite และ redirect, sitemap
   และไฟล์ยืนยันสิทธิ์ Search Console ของพวกนี้ไม่ได้อยู่ในฐานข้อมูลเนื้อหา
   จึงไม่ติดไปกับการ export เนื้อหา
3. **ตรวจว่า redirect ถาวรยังถาวรอยู่** บนโฮสต์ใหม่ ให้ยิงดูว่ายังตอบด้วยรหัสถาวรเหมือนเดิมไหม
   ค่าตั้งต้นของเซิร์ฟเวอร์และการสร้างกฎใหม่โดยเฟรมเวิร์ก มัก**ลดชั้นจากถาวรเป็นชั่วคราวเอง**
   ทั้งที่ไม่มีใครตั้งใจไปแก้กฎ
4. **ลด TTL ของ DNS ก่อนวันสลับ** เพื่อให้เปลี่ยนแล้วกระจายเร็ว และถ้าจะถอยกลับก็ถอยได้เร็วเท่ากัน
5. **ทดสอบก่อนด้วยการปักไฟล์ hosts** ชี้ hosts ในเครื่องตัวเองไปที่ IP ของเซิร์ฟเวอร์ใหม่
   แล้วเดินดูทั้งเว็บ รวมทั้งตาราง redirect ไฟล์ robots และ sitemap **ก่อนแตะ DNS**
6. **หลังสลับของ ให้เฝ้าดู 4xx และ 5xx ใน log** error ใหม่ใน log คือสัญญาณที่มาเร็วที่สุด
   และเชื่อถือได้ที่สุดว่ามีอะไรในตารางหรือบนโฮสต์ผิด

## ขั้นที่ 5 กับดัก redirect สองอย่างที่ต้องรู้

**หนึ่ง redirect หน้าแรกวนลูปเพราะไฟล์ default** หน้าแรกเข้าได้สองทาง
คือที่โฟลเดอร์เปล่า (`/`) กับที่ชื่อไฟล์ default ของมัน เช่น `/index.html`
วิธีแก้แบบตรงไปตรงมาคือ 301 จากชื่อไฟล์ไปที่โฟลเดอร์เปล่า **แล้วมันจะวนไม่รู้จบ**
เพราะข้างในเซิร์ฟเวอร์เสิร์ฟโฟลเดอร์เปล่าด้วยไฟล์ default นั่นเอง กฎเลยถูกจุดชนวนซ้ำ
**วิธีแก้คือผูกเงื่อนไขกับบรรทัดคำขอที่ client ส่งมาจริง ๆ ไม่ใช่กับ path ที่เซิร์ฟเวอร์แปลงแล้วข้างใน**
การแปลง path ข้างในจะได้ไม่เข้าเงื่อนไข **ตรวจด้วยการยิงทั้งสองแบบ ต้องได้ 301 หนึ่งทอดแล้ว 200 ไม่ใช่วนลูป**

**สอง rewrite กับ redirect ยิงใส่กันเอง** เมื่อ rewrite ภายในกับ redirect ภายนอกชี้ไปที่ผลของกันและกัน
คือ rewrite แปลง URL สวยไปเป็นไฟล์จริง ส่วน redirect แปลงไฟล์จริงกลับมาเป็น URL สวย
กฎทั้งคู่จะจุดชนวนซ้ำบนผลของอีกฝ่ายแล้ววนลูป
**แก้ด้วยพารามิเตอร์ธง** ให้ rewrite ภายในต่อพารามิเตอร์ที่เป็นเครื่องหมายไว้ท้าย URL
แล้วตั้งเงื่อนไขให้กฎ redirect ข้ามคำขอที่มีเครื่องหมายนั้น
**ธงนี้ต้องไม่โผล่ใน URL ที่ผู้ใช้เห็น** มันมีชีวิตอยู่แค่ช่วงข้ามเส้น rewrite ภายในเท่านั้น
ตรวจแบบเดียวกัน คือหนึ่งทอดแล้ว 200

## ขั้นที่ 6 ความคาดหวังหลังย้าย และการทยอยย้าย

- **หลังย้าย traffic ตกลงชั่วคราวเป็นเรื่องปกติ ให้คาดว่าจะฟื้นภายในระยะเวลาหนึ่ง
  ซึ่งต้องตกลงกับลูกค้าไว้ล่วงหน้าก่อนเริ่มงาน** เว็บใหญ่มากที่เปลี่ยนทั้งโดเมนและทุก URL พร้อมกัน
  ใช้เวลานานกว่านั้นได้ **การตกภายในกรอบที่ตกลงกันไว้ ไม่ใช่หลักฐานว่าการย้ายล้มเหลว
  อย่าเพิ่งไปรื้อตารางที่ถูกต้องอยู่แล้วเพราะสัปดาห์ที่สามดูไม่ดี**
- **ใช้ปริมาณการ crawl เป็นตัววัดความคืบหน้า** ก่อนสลับของ ให้บันทึกอัตราการ crawl ของเว็บเดิมจาก server log
  ไว้เป็นค่าตั้งต้น หลังสลับของ ให้เทียบปริมาณการ crawl ของโดเมนใหม่กับค่าตั้งต้นนั้น
  พอเข้าใกล้ของเดิมคือสัญญาณว่าเครื่องมือค้นหาประมวลผลและเชื่อการย้ายแล้ว
  ดูแนวโน้ม traffic จากการค้นหาควบคู่ไปด้วย
  **วิธีนี้เปลี่ยน "ตกเป็นเรื่องปกติ รอไปก่อน" ให้กลายเป็นตัวเลขความคืบหน้าที่ลูกค้าดูเองได้ทุกสัปดาห์**
- **ทางเลือกทยอยย้าย** เสนอให้ย้ายทีละส่วนของเว็บได้ เพื่อเปลี่ยนความเสียหายก้อนลึกก้อนเดียว
  ให้เป็นก้อนเล็กหลายก้อนที่ดูออกและแก้ได้ทีละก้อน
- **ปล่อย sitemap ทั้งสองชุดไว้ก่อน** ทั้ง URL เก่าและ URL ใหม่ จนกว่า redirect จะถูกเก็บครบ
  บอทจะได้เห็นทั้งสองฝั่งของตาราง

## ขั้นที่ 7 ห้ามรื้อ URL ที่ติดอันดับอยู่แล้วเพื่อยัดคีย์เวิร์ด

**ห้ามเปลี่ยน URL ที่ติดอันดับอยู่แล้ว เพียงเพื่อใส่คีย์เวิร์ดลงไปใน path**
ของที่ได้เพิ่มมีน้อย ความเสียหายจากการย้ายเกิดขึ้นแน่นอน
และผลลัพธ์ที่ดีที่สุดเท่าที่จะเป็นไปได้คือกลับไปอยู่อันดับเดิมที่มีอยู่แล้ว
การรื้อ URL เพื่อคีย์เวิร์ดคือการย้ายเว็บที่รับความเสี่ยงเต็มจำนวนโดยไม่มีของตอบแทน
**คำตอบของสกิลนี้ต่อคำขอแบบนั้นคือไม่**

## ขั้นที่ 8 เขียนแผนและส่งมอบ

ชื่อไฟล์ต้องเป็นแบบนี้

```
work/{domain}/(00-baseline|01-current)/{domain}_seo-migration_{YYYY-MM-DD}.md
```

1. **ประเภทการย้าย** และประเภทที่ซ้อนกันอยู่
2. **ตาราง URL เก่าไปใหม่** พร้อมบอกว่ารวบรวมจากแหล่งไหนบ้าง และมีกี่ URL ที่ยังไม่มีปลายทาง
3. **ลำดับงานและวันที่** ใครทำอะไรก่อนหลัง
4. **checklist ที่ต้องผ่านก่อนสลับของ** ทำเป็นช่องติ๊ก ไม่ใช่เล่าเป็นความเรียง
5. **แผนถอยกลับ** ถ้าสลับแล้วพัง จะถอยยังไงและใช้เวลาเท่าไร
6. **สิ่งที่จะเฝ้าดูหลังย้าย** และตกลงกันไว้ว่าจะดูนานแค่ไหนก่อนสรุปผล
7. **ส่งต่อให้สกิลไหน**

## การวางไฟล์ผลลัพธ์

สกิลนี้อยู่ในชุดที่ใช้โครงโฟลเดอร์ของสกิล `new-workspace-lite`

1. ผลลัพธ์ทุกไฟล์อยู่ใต้ `work/{domain}/`
2. ถ้า `work/{domain}/00-baseline/` ยังไม่มีไฟล์หัวข้อเดียวกัน ให้เขียนลง `00-baseline/` ถ้ามีแล้ว ให้เขียนลง `01-current/`
3. เขียนเสร็จ ให้เพิ่มบรรทัดลงตารางใน `work/{domain}/CHANGELOG.md` ว่าวันที่ รันสกิลอะไร ได้ไฟล์อะไร
4. ถ้ายังไม่มี `work/{domain}/` ให้แนะนำผู้ใช้รันสกิล `new-workspace-lite` ก่อน ห้ามสร้างโครงเองแบบอื่น

## ขอบเขต ใครดูอะไร

**สกิลนี้ดู** วิธีทำตาราง URL เก่าไปใหม่ ลำดับขั้นเปลี่ยนโดเมนและการแจ้งย้ายที่อยู่
ด่านตรวจโดเมนต้นทาง checklist ย้ายโฮสต์ ความคาดหวังหลังย้ายและการทยอยย้าย
กฎห้ามรื้อ URL เพื่อคีย์เวิร์ด และกับดัก redirect สองอย่างข้างบน

| เรื่อง | ใครดู |
|---|---|
| ตรวจ redirect บนเว็บที่ขึ้นระบบไปแล้ว ว่าต่อกันเป็นทอด วนลูป หรือรหัสผิด | `technical-audit-lite` |
| สร้าง sitemap ชุดใหม่หลังย้าย | `sitemap-architecture-lite` |
| ประเมินคุณภาพลิงก์ที่ชี้เข้าโดเมนต้นทาง ก่อนตัดสินด่านในขั้นที่ 3 | `seo-backlink-strategy-lite` |

**ลำดับในสายงาน** สกิลนี้ทำก่อนวันสลับของ แล้ว `sitemap-architecture-lite` สร้าง sitemap ชุดใหม่
ตามด้วย `technical-audit-lite` ตรวจว่าของที่ทำไปทำงานจริง

## กฎ

- **ถ้าดึงข้อมูลไม่สำเร็จ ให้เขียนว่า `ตรวจไม่ได้` ห้ามเขียนว่า `ไม่มี`** สองคำนี้คนละความหมาย ถ้าเขียนผิดผู้ใช้จะสรุปกลับด้าน
- **ทำได้บางส่วนต้องส่งส่วนนั้นเสมอ** ห้ามส่งตารางที่ทุกช่องว่าง และห้ามปฏิเสธทั้งงานเพราะขาดข้อมูลบางอย่าง ให้ติดป้ายว่าข้อไหนยืนยันแล้ว ข้อไหนต้องยืนยันเพิ่ม · การใช้ข้อจำกัดเป็นข้ออ้างไม่ส่งงาน ไม่ใช่ความซื่อสัตย์
- **ห้ามแก้ไฟล์บนเว็บจริง ห้ามตั้ง redirect เอง ห้ามแตะ DNS** สกิลนี้ทำแผนและตารางให้ คนเป็นผู้ลงมือ
- **ห้ามให้คะแนนความเสี่ยงเป็นตัวเลข** ใช้ พร้อมย้าย ยังไม่พร้อม ห้ามย้าย
- **ห้ามสัญญาว่าอันดับจะไม่ตก** และ**ห้ามระบุจำนวนวันหรือสัปดาห์ที่จะฟื้นเป็นตัวเลขตายตัว**
  ให้ตกลงกรอบเวลากับลูกค้าไว้ล่วงหน้า แล้ววัดความคืบหน้าจากปริมาณการ crawl ของเว็บนั้นเอง
- **ห้ามตกลงวันขึ้นระบบก่อนตาราง URL จะครบ** เจอตารางไม่ครบให้บอกตรง ๆ ว่าต้องเลื่อน
- **ห้ามให้ redirect ต่อกันเป็นทอดยาว** ทุกแถวควรถึงปลายทางในทอดเดียว เจอทอดซ้อนให้ยุบให้เหลือทอดเดียว
- ถ้าข้อมูลไม่พอให้เขียนตรง ๆ ว่าไม่พอ และบอกว่าต้องใช้อะไรเพิ่ม
