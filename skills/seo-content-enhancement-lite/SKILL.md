## Client workspace routing (mandatory for file changes)

Every generated file has exactly one home. Audit, keyword and comparison
outputs live under `work/{domain}/` created by `new-workspace-lite`
(`00-baseline/` first run, `01-current/` later runs, `02-fixes/`, `03-content/`,
`04-reports/`, `uploads/` read-only for user files); never invent another
top-level folder there. Content production and WordPress publishing use the
client workspace `clients/<client>/` created by `new-client-lite`: read
`workspace-routing.json` first, resolve every artifact with
`{PLUGIN_ROOT}/skills/rainmojo-so-lite/scripts/client_workspace.py route`, use the
most precise registered route, edit root files only when their exact filename is
in `root_policy.allowed_files`, treat `uploads/` as read-only, and when no route
fits use `create-work` then `route-work`; never construct a `work/<name>/...`
path by hand inside a client workspace. Never write generated files to the
plugin tree or the caller's working directory. Append one line to the
workspace's `CHANGELOG.md` or `log.md` after every write. Run
`client_workspace.py validate` before handing a client workspace over. Direct
CMS/API operations retain their own safety and verification gates.

## Presentation (Two-Tier, 7 modes)

Answer in the response mode that matches the request
(`{PLUGIN_ROOT}/skills/rainmojo-so-lite/_base/presentation-scaffold.md`): quick fact,
how-to, comparison, troubleshoot, audit, deployable, always closing with next
steps. A run that writes a deliverable ends with a Tier 1 card built from
`summary.json` (`templates/widget/summary.schema.json`) and rendered with
`{PLUGIN_ROOT}/skills/rainmojo-so-lite/scripts/present.py --target auto`, then hands
off to the Tier 2 file, which stays complete and unchanged. Lite cards carry
counts of checks passed, never a weighted score. Every card value is copied
from the deliverable; unmeasured values show as could not verify. No emoji on
any surface; the glyph allowlist applies to chat and Markdown only.


# SEO Content Enhancement

ยึดหลัก QEG ย่อ 6 ข้อเป็นแกน ประเมินเป็นระดับ ดี พอใช้ ต้องแก้ เท่านั้น
ขั้นตอนเต็มอยู่ใน [agent.json](agent.json)

## หลัก QEG ย่อ 6 ข้อ

| # | หลัก | ก่อน | หลัง |
|---|---|---|---|
| 1 | **ตอบก่อน ขยายทีหลัง** เปิด section ด้วยคำตอบใน 1-2 ประโยค | "วันนี้มีคำตอบมาฝาก" | "สนามหญ้าเทียมใช้ปุ่ม TF ปุ่มสั้นถี่ ไม่กินข้อเข่า" |
| 2 | **เขียนเพื่อคนอ่าน ห้ามยัดคำค้น** | "รับทำ SEO ราคาถูก บริการ SEO คุณภาพ" | "วิเคราะห์คำค้นจริงของลูกค้า แล้วปรับเว็บทีละหน้า" |
| 3 | **ประสบการณ์ต้องมีรายละเอียด** | "เราคือผู้เชี่ยวชาญอันดับหนึ่ง" | "เคสที่เจอบ่อยคือถอดรีเทนเนอร์เร็วไปจนฟันล้มกลับ" |
| 4 | **หัวข้อตรงเนื้อหา ไม่ clickbait** | "คู่มือฉบับสมบูรณ์ ทุกสิ่งที่ควรรู้" | "ประกันชั้น 1 กับ 2+ ต่างกันตรงไหน" |
| 5 | **ทุกข้ออ้างมีที่มา** | "งานวิจัยชี้ว่าคนไทย 90% มีปัญหาฟัน" | ระบุชื่อแหล่งและปี หาไม่ได้ให้ตัดตัวเลขทิ้ง |
| 6 | **YMYL ต้องแม่นเป็นพิเศษ** | "สมุนไพรนี้รักษาเบาหวานได้ หยุดยาได้" | "ยังไม่มีหลักฐานว่าใช้แทนยาได้ ควรปรึกษาแพทย์" |

## ขั้นที่ 0 ดึง HTML ดิบก่อน เฉพาะกรณีที่มี URL หน้าเดิม

**ต้องทำก่อนขั้นที่ 1 ทุกครั้งที่ผู้ใช้ให้ URL หน้าเดิมมา** เพราะ WebFetch คืนเนื้อหาที่แปลงเป็นข้อความแล้ว
แท็กใน `<head>` อย่าง title และ meta description ถูกตัดทิ้งตอนแปลง
ถ้าดูจากผล WebFetch อย่างเดียว จะรายงานว่าหน้าเดิมไม่มี title หรือไม่มี description ทั้งที่มีอยู่จริง

```bash
mkdir -p work/{domain}/uploads
curl -sSL -A "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 Chrome/120" \
  -m 25 "{URL หน้าเดิม}" -o work/{domain}/uploads/page.html
```

**แล้วใช้ Grep กับไฟล์ที่ดาวน์โหลดมา** ไม่ใช่กับผล WebFetch โดยหา `<title` และ `name="description"`
ส่วนเนื้อหาในตัวหน้าที่ใช้ประเมินตามหลัก 6 ข้อ ยังอ่านจากผล WebFetch ได้ตามเดิม

### ถ้าใช้คำสั่งพวกนี้ไม่ได้

**บาง host ไม่มีเครื่องมือรันคำสั่งให้** เช่น Cowork, Claude Desktop และ GPT desktop
ถ้าเป็นแบบนั้น ให้ทำแบบนี้แทน แล้วงานจะยังเดินต่อได้

1. บอกผู้ใช้ว่า **ขอให้ช่วยเปิดหน้าเว็บแล้วคัดลอกซอร์สมาให้**
   วิธีคือเปิดหน้านั้นในเบราว์เซอร์ กด `Ctrl+U` หรือ `Cmd+Option+U` เพื่อดู source
   แล้วเลือกทั้งหมด คัดลอก มาวางในแชท
2. ถ้าผู้ใช้ทำให้ได้ ให้ทำงานต่อจากซอร์สที่ได้มา ตามขั้นตอนเดิมทุกอย่าง
3. ถ้าผู้ใช้ไม่สะดวก ให้ใช้ WebFetch เท่าที่ได้ แล้วเขียนกำกับว่า title และ meta description เดิม **ตรวจไม่ได้**
   ห้ามเขียนว่า `ไม่มี` และ **ห้ามหยุดงาน** ให้เขียนของใหม่ต่อไปตามขั้นที่ 4

**บน Windows** ถ้ารันแล้วขึ้นว่าไม่รู้จักคำสั่ง ให้ลองใน Git Bash หรือ WSL
ถ้าไม่มีทั้งสองอย่าง ให้ใช้วิธีคัดลอกซอร์สในข้อ 1

เขียนเนื้อหาใหม่ทั้งหน้าและยังไม่มี URL เดิม ให้ข้ามขั้นนี้ไปที่ขั้นที่ 1 ได้เลย

## ขั้นที่ 1 เก็บข้อมูลและจำแนก intent

| ต้องรู้ | กติกา |
|---|---|
| หัวข้อ คำค้นหลัก กลุ่มผู้อ่าน | ถามผู้ใช้ ห้ามเดา |
| แบรนด์และจุดต่าง | ใช้เฉพาะที่ผู้ใช้ให้ ไม่ให้ก็ใช้โทนกลาง ห้ามแต่งเอง |
| URL หน้าเดิม | มีคือปรับปรุงของเก่า ไม่มีคือเขียนใหม่ |
| intent | Know ตอบตรงมีหลักฐาน / Do ขั้นตอนเรียงลำดับ / Website ตัวตนชัด / Visit-in-Person ที่อยู่ เวลาเปิด |
| YMYL | กระทบสุขภาพ การเงิน กฎหมาย ความปลอดภัย ให้ติดธง ตรวจข้อเท็จจริงเข้มขึ้น และต้องมี disclaimer |

**ปรับปรุงของเก่า** ใช้ WebFetch ดึงหน้ามา ประเมินทีละ section เทียบหลัก 6 ข้อ ทำตาราง หลัก / ระดับ / ปัญหา
ส่วน title และ meta description เดิม ให้อ่านจากไฟล์ HTML ดิบในขั้นที่ 0 เท่านั้น ห้ามสรุปจากผล WebFetch
ดึงไฟล์ดิบไม่สำเร็จ ให้ลงว่า **ตรวจไม่ได้** ในตาราง แล้วทำหัวข้ออื่นต่อ ห้ามหยุดทั้งงาน

## ขั้นที่ 2 วางโครง

โครงบังคับคือ H1 แล้วบทนำ แล้ว H2 พร้อมย่อหน้าเปิด แล้ว H3 เมื่อจำเป็น แล้วสรุป แล้ว FAQ
บทนำต้องมีก่อน H2 แรกเสมอ หนึ่งประเด็นต่อหนึ่ง H2 ใช้ H3 เมื่อ H2 ยาวจนต้องแบ่ง ห้ามข้ามลำดับ
H1 มีคำค้นหลัก ห้าม generic แบบ "ยินดีต้อนรับ" สรุปย้ำคำตอบหลักไม่เปิดประเด็นใหม่

## ขั้นที่ 3 เขียน

เปิดทุก section ด้วยคำตอบตามหลักข้อ 1 ย่อหน้าละ 2-4 ประโยค ใช้ตารางเมื่อเทียบ 3 อย่างขึ้นไป

| สำนวนต้องห้าม | ใช้แทน |
|---|---|
| คู่มือฉบับสมบูรณ์, แบบครบถ้วน | หัวข้อที่บอกประเด็นจริง |
| ทุกสิ่งที่คุณควรรู้ | บอกขอบเขตจริงของเนื้อหา |
| ประกาศว่าตัวเองเชี่ยวชาญลอย ๆ | จากเคสที่เราเจอบ่อย, ในการทำงานจริงพบว่า |
| Furthermore, Moreover แปลตรงตัว | พูดง่าย ๆ คือ, อีกมุมหนึ่งคือ |

เขียนเสร็จให้ Grep หาสำนวนต้องห้ามทั้งไฟล์ ต้องเจอเป็นศูนย์ เจอที่ไหนให้เขียนใหม่

### หลักฐานต้องไม่วนกลับหาตัวเอง ทำระหว่างขั้นที่ 3

ต่อจากหลักข้อ 5 ทุกข้ออ้างที่ใส่หลักฐานกำกับ ต้องอ้างถึง **แหล่งต้นทางของข้อมูลนั้น**
คือคนที่ทำข้อมูลนั้นขึ้นมาเอง เช่น งานวิจัย แบบสำรวจ ชุดข้อมูล หรือองค์กรที่เป็นผู้ประกาศค่านั้น

**ลิงก์ไปหน้าอื่นในเว็บเดียวกันที่แค่พูดเรื่องเดิมซ้ำ ไม่นับเป็นหลักฐาน** นี่คือการอ้างวนกลับหาตัวเอง
ต่อให้จัดรูปแบบถูกต้องทุกอย่างก็ยังไม่นับ เพราะรูปแบบที่ถูกไม่ได้ทำให้การอ้างวนกลายเป็นหลักฐาน

**วิธีตรวจคือไล่ลิงก์หลักฐานของทุกข้ออ้างออกไปหนึ่งขั้น แล้วดูว่าปลายทางคืออะไร**

| ปลายทางที่เปิดดูแล้ว | ผล |
|---|---|
| แหล่งภายนอกที่เป็นคนทำข้อมูลนั้นเอง | ผ่าน นับเป็นหลักฐาน |
| หน้าในเว็บเดียวกันที่แค่พูดซ้ำ ไม่ได้เป็นคนทำข้อมูล | ไม่ผ่าน ไม่นับเป็นหลักฐาน |
| หน้าในเว็บเดียวกันที่เป็นคนทำข้อมูลนั้นจริง เช่น ผลสำรวจที่เราเก็บเอง | ผ่าน และหน้านั้นต้องเขียนวิธีเก็บข้อมูลไว้ด้วย |
| เปิดปลายทางไม่ได้ | ลงว่า `ตรวจไม่ได้` ห้ามสรุปว่าเป็นการอ้างวน และห้ามนับเป็นหลักฐาน |

ลิงก์ภายในที่ไม่ผ่านข้อนี้ **ยังอยู่บนหน้าได้ในฐานะลิงก์ภายใน** ตามแผนของสกิล `seo-internal-linking-lite`
แต่ต้องถอดสถานะการเป็นหลักฐานออก แล้วไปหาแหล่งต้นทางจริงมาเติมให้ข้ออ้างนั้น
หาไม่ได้ให้ลดระดับคำพูดลงหรือตัดตัวเลขนั้นทิ้ง ตามหลักข้อ 5

เคสที่ข้อนี้ปิดคือหน้าที่ลิงก์ภายในครบสวยงาม แต่ทุกข้ออ้างชี้กลับไปที่บทความของตัวเองทั้งหมด
โดยไม่มีการยืนยันจากภายนอกเลยแม้แต่จุดเดียว

## ขั้นที่ 4 title และ meta description

| รายการ | เกณฑ์ |
|---|---|
| ความยาว | title 50 ถึง 60 ตัวอักษร, description 140 ถึง 160 ตัวอักษร |
| วิธีนับ | เหมือนสกิล meta-basics-lite คือ สระบน สระล่าง วรรณยุกต์ นับเป็น 1 ตัวเสมอ ไล่นับทีละตัว |
| แบรนด์ | ใส่เฉพาะ title หน้าแรก วางหน้าสุด หน้าอื่นห้ามใส่ |
| ห้ามใช้ | em dash และ pipe ใน title, description, heading, เนื้อหา |

หน้าบริการ ผิดคือ "รับทำ SEO ติดอันดับ กับ BIQDADDY" ถูกคือ "บริการรับทำ SEO เพิ่มยอดขาย และรองรับ AI Search"

## ขั้นที่ 5 ตรวจก่อนส่ง

เดิน checklist ทั้ง 8 ข้อใน `workflow.checklist` ของ [agent.json](agent.json)
บันทึกทุกข้อเป็น ผ่าน หรือ ไม่ผ่าน ข้อไม่ผ่านให้กลับไปแก้แล้วตรวจซ้ำ ห้ามส่งงานที่ยังไม่ผ่านโดยไม่แจ้ง

## ผลลัพธ์

ไฟล์เดียว ตั้งชื่อและวางตาม path นี้เป๊ะ

```
work/{domain}/(00-baseline|01-current)/{domain}_content-enhancement_{YYYY-MM-DD}.md
```

เรียงหัวข้อในไฟล์ สรุป intent สถานะ YMYL กลุ่มผู้อ่าน / ตารางผลประเมินหน้าเดิม /
โครงที่ใช้ / เนื้อหาฉบับเต็ม / meta พร้อมจำนวนตัวอักษร /
ตารางไล่ปลายทางลิงก์หลักฐานหนึ่งขั้น หนึ่งแถวต่อหนึ่งข้ออ้างที่มีหลักฐาน / ผล checklist

## การวางไฟล์ผลลัพธ์

สกิลนี้อยู่ในชุดที่ใช้โครงโฟลเดอร์ของสกิล `new-workspace-lite`

1. ผลลัพธ์ทุกไฟล์อยู่ใต้ `work/{domain}/`
2. ถ้า `work/{domain}/00-baseline/` ยังไม่มีไฟล์หัวข้อเดียวกัน ให้เขียนลง `00-baseline/` ถ้ามีแล้ว ให้เขียนลง `01-current/`
3. เขียนเสร็จ ให้เพิ่มบรรทัดลงตารางใน `work/{domain}/CHANGELOG.md` ว่าวันที่ รันสกิลอะไร ได้ไฟล์อะไร
4. ถ้ายังไม่มี `work/{domain}/` ให้แนะนำผู้ใช้รันสกิล `new-workspace-lite` ก่อน ห้ามสร้างโครงเองแบบอื่น

## กฎ

- **ห้ามเดาตัวเลข ห้ามแต่งสถิติหรือคำรับรอง** ไม่มีแหล่งจริงให้ตัดออก
- **ห้ามนับลิงก์ไปหน้าอื่นในเว็บเดียวกันที่แค่พูดซ้ำ เป็นหลักฐานของข้ออ้าง**
  ต้องไล่ปลายทางหนึ่งขั้นก่อนเสมอ เปิดปลายทางไม่ได้ให้ลงว่า `ตรวจไม่ได้` และยังไม่นับเป็นหลักฐาน
- **ห้ามให้คะแนนเป็นตัวเลข** ใช้ ดี พอใช้ ต้องแก้ และ ผ่าน ไม่ผ่าน เท่านั้น
- ห้ามแต่งแบรนด์ จุดต่าง หรือประสบการณ์ที่ผู้ใช้ไม่ได้ให้
- YMYL ห้ามฟันธงเกินหลักฐาน ต้องมี disclaimer เสมอ
- ห้ามใช้สำนวนต้องห้าม และห้ามใส่แบรนด์ใน title ยกเว้นหน้าแรก
- **ดึงข้อมูลไม่สำเร็จ ให้เขียนว่า `ตรวจไม่ได้` ห้ามเขียนว่า `ไม่มี`** สองคำนี้คนละความหมาย
  เขียนผิดจะทำให้ผู้ใช้สรุปกลับด้าน เช่น ไปเพิ่ม meta description ซ้ำทั้งที่หน้านั้นมีอยู่แล้ว
- **ทำได้บางส่วนต้องส่งส่วนนั้น** ห้ามส่งตารางที่ทุกช่องเขียนว่าประเมินไม่ได้
