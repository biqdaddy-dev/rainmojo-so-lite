# Technical Audit

ตอบคำถามเดียวคือ **มีอะไรในเว็บที่ขวางไม่ให้คนและบอทเข้าถึงเนื้อหา** เน้น SEO ดั้งเดิม

## ขอบเขต ใครดูอะไร

| เรื่อง | ใครดู |
|---|---|
| ความเร็ว มือถือ HTTPS การเข้าดัชนี เนื้อหาใน HTML | **สกิลนี้** |
| robots.txt และรายชื่อ AI crawler | `aiso-crawlers-lite` |
| ความพร้อมฝั่งบอท AI และ security header | `aiso-technical-lite` |
| structured data กับ llms.txt | `aiso-schema-lite` และ `aiso-llmstxt-lite` |

**ห้ามตรวจซ้ำงานสกิลอื่น** เจอเรื่องนอกขอบเขตให้จดหนึ่งบรรทัดแล้วบอกให้รันสกิลนั้น
มีไฟล์ผลของสกิลนั้นใน `work/{domain}/` แล้ว ให้อ้างชื่อไฟล์แทนการตรวจใหม่
**รายชื่อ AI crawler ใช้ชุดเดียวกับ `aiso-crawlers-lite` ห้ามเขียนรายชื่อขึ้นเอง**

## ระดับผลที่ใช้ทั้งไฟล์

| ระดับ | หมายถึง |
|---|---|
| **ผ่าน** | ไม่พบปัญหา |
| **ควรดู** | ใช้ได้ แต่ดีขึ้นได้ ใส่ในแผนเดือนนี้ |
| **มีปัญหา** | ขวางคนหรือบอทจริง แก้ก่อนอย่างอื่น |
| **ตรวจไม่ได้** | ข้อมูลไม่พอ ต้องบอกว่าขาดอะไร |

## ขั้นที่ 0 ดึง HTML ดิบมาเก็บไว้ก่อน

**ต้องเก็บ header ด้วย GET เท่านั้น ห้ามใช้ `curl -I` หรือ `-sSI`** เพราะบางเซิร์ฟเวอร์ตอบ
HEAD กับ GET ไม่เหมือนกัน เช่นส่ง `strict-transport-security` ให้เฉพาะ HEAD
ถ้าเก็บด้วย HEAD จะสรุปเรื่องความปลอดภัยและแคชกลับด้านจากที่ผู้ใช้จริงเจอ
ใช้ `-D` แนบกับการดึงหน้าปกติ ได้ทั้งไฟล์ HTML และ header จากคำขอเดียวกัน

**ต้องทำก่อนขั้นอื่นทั้งหมด** เพราะ WebFetch คืนเนื้อหาที่แปลงเป็นข้อความแล้ว
แอตทริบิวต์อย่าง `src` `href` และแท็กใน `<head>` ถูกตัดทิ้ง
ถ้าตรวจจากผล WebFetch อย่างเดียว จะรายงานว่า ไม่มี ทั้งที่มีอยู่ ซึ่งเป็นผลลบลวง

```bash
mkdir -p work/{domain}/uploads
curl -sSL -D work/{domain}/uploads/home-headers.txt \
  -A "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 Chrome/120" \
  -m 25 "https://{domain}/" -o work/{domain}/uploads/home.html
```

### ถ้าใช้คำสั่งพวกนี้ไม่ได้

**บาง host ไม่มีเครื่องมือรันคำสั่งให้** เช่น Cowork, Claude Desktop และ GPT desktop
ถ้าเป็นแบบนั้น ให้ทำแบบนี้แทน แล้วงานจะยังเดินต่อได้

1. บอกผู้ใช้ว่า **ขอให้ช่วยเปิดหน้าเว็บแล้วคัดลอกซอร์สมาให้**
   วิธีคือเปิดหน้านั้นในเบราว์เซอร์ กด `Ctrl+U` หรือ `Cmd+Option+U` เพื่อดู source
   แล้วเลือกทั้งหมด คัดลอก มาวางในแชท
2. ถ้าผู้ใช้ทำให้ได้ ให้ทำงานต่อจากซอร์สที่ได้มา ตามขั้นตอนเดิมทุกอย่าง
3. ถ้าผู้ใช้ไม่สะดวก ให้ใช้ WebFetch เท่าที่ได้ แล้ว**เขียนกำกับทุกหัวข้อที่กระทบว่า `ตรวจไม่ได้`**
   ห้ามเขียนว่า `ไม่มี` เพราะสองคำนี้คนละความหมาย และการเขียนผิดจะทำให้ผู้ใช้เข้าใจกลับด้าน

**บน Windows** ถ้ารันแล้วขึ้นว่าไม่รู้จักคำสั่ง ให้ลองใน Git Bash หรือ WSL
ถ้าไม่มีทั้งสองอย่าง ให้ใช้วิธีคัดลอกซอร์สในข้อ 1

ทำแบบเดียวกันกับหน้าสำคัญอีก 2 หน้า เช่น หน้าบริการและหน้าติดต่อ

**แล้วค่อยใช้ Grep กับไฟล์ที่ดาวน์โหลดมา** ไม่ใช่กับผล WebFetch

ถ้า `curl` ใช้ไม่ได้ในเครื่องผู้ใช้ ให้บอกตรง ๆ แล้วทำเท่าที่ WebFetch ให้ได้
พร้อมเขียนกำกับทุกหัวข้อที่กระทบว่า **ตรวจไม่ได้** ห้ามเขียนว่า ผ่าน

## ขั้นที่ 0.5 อ่าน response header

จากไฟล์ `home-headers.txt` ที่ดึงมา ให้ดู

| หัวข้อ | ดูอะไร | ผลที่ควรได้ |
|---|---|---|
| สถานะ | บรรทัดแรกเป็น 200 ไหม | ผ่าน |
| บีบอัด | มี `content-encoding` เป็น gzip หรือ br ไหม | ถ้าไม่มี ควรดู |
| แคช | มี `cache-control` ไหม และไม่ใช่ `no-store` | ถ้าไม่มี ควรดู |
| ความปลอดภัย | มี `strict-transport-security` ไหม | ถ้าไม่มี ควรดู |
| การเก็บหน้า | มี `x-robots-tag` ที่เขียน noindex ไหม | ถ้ามีบนหน้าที่อยากติด คือมีปัญหา |

## ขั้นที่ 1 ประกาศขอบเขต

ถามว่าจะตรวจกี่หน้า ไม่ตอบให้เลือกหน้าแรกอย่างเดียว แล้วเขียนข้อจำกัดกำกับ

- หน้าแรกอย่างเดียว ผลอธิบายได้แค่หน้าแรก ไม่ใช่ทั้งเว็บ
- ตัวแทนแม่แบบ เช่น บทความ บริการ หมวด แม่แบบอื่นยังไม่ได้ดู
- ทุก URL ใน sitemap หน้าที่ไม่อยู่ใน sitemap ยังไม่ได้ดู

**เขียนขอบเขตเป็นหัวข้อแรกของรายงานเสมอ** ไม่งั้นคนอ่านจะคิดว่าตรวจครบทั้งเว็บ

## ขั้นที่ 2 เข้าถึงหน้าเว็บได้ไหม

| ทำอะไร | ผ่านเมื่อ |
|---|---|
| WebFetch ที่ URL | ได้เนื้อหา ไม่ใช่หน้า error |
| เปิด `http://` และแบบมี www | เด้งมา https ปลายทางเดียวกัน ในทอดเดียว |
| เปิด https | ไม่มีคำเตือนเรื่องใบรับรอง |
| Grep `src="http://` และ `href="http://` ในไฟล์ HTML ดิบที่ดึงมาในขั้นที่ 0 | ไม่พบในหน้า https |

เปิดเว็บไม่ได้เลยให้หยุด รายงานว่าเข้าไม่ได้ **ห้ามแต่งผลข้ออื่นต่อ**

## ขั้นที่ 3 ความเร็ว

**ห้ามข้ามขั้นนี้หรือโยนกลับให้ผู้ใช้ทั้งหมด** ความเร็วคือคำถามแรกของงานนี้
วัดเองได้สามอย่างจากเครื่องมือที่มีอยู่แล้ว ทุกตัวเป็นการวัดจริง ไม่ใช่การเดา

**หนึ่ง เวลาตอบสนองของเซิร์ฟเวอร์** ยิง 3 ครั้งแล้วรายงานค่ากลาง

```bash
for i in 1 2 3; do
  curl -sS -o /dev/null -w 'ครั้งที่ %{num_redirects}: TTFB %{time_starttransfer}s รวม %{time_total}s
'     -A "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 Chrome/120" -m 25 "https://{domain}/"
done
```

**สอง น้ำหนักหน้า** ไล่รายการ `src` ของรูปและ `href` ของ CSS กับ `src` ของ JS
จากไฟล์ HTML ดิบในขั้นที่ 0 แล้วชั่งทีละไฟล์ อย่างน้อยรูป 10 ไฟล์แรก

```bash
grep -o 'src="[^"]*\.\(png\|jpg\|jpeg\|webp\|avif\|gif\)[^"]*"' work/{domain}/uploads/home.html | head -10
curl -sSL -o /dev/null -w '%{size_download} bytes  %{url_effective}
' -m 25 "URL รูปทีละไฟล์"
```

รายงานเป็นตัวเลขไบต์จริง แล้วชี้ไฟล์ที่หนักที่สุด **รูปเดียวที่ใหญ่เกินหนึ่งเมกะไบต์
มักเป็นตัวถ่วงหลักของทั้งหน้า และเป็นงานแก้ที่คุ้มที่สุด**

**สาม อายุใบรับรอง SSL** ดูว่าใครออกและหมดเมื่อไร

```bash
echo | openssl s_client -servername {domain} -connect {domain}:443 2>/dev/null | openssl x509 -noout -issuer -enddate
```

รายงานวันหมดอายุจริงและจำนวนวันที่เหลือเสมอ ห้ามเขียนคำว่าเกณฑ์หรือใส่ตัวเลขวันของเราเองลงไป
เพราะลูกค้าจะอ่านว่าเป็นมาตรฐานอุตสาหกรรม ใบรับรองส่วนใหญ่ต่ออายุอัตโนมัติล่วงหน้าอยู่แล้ว
ให้ยกเป็นข้อสังเกตเมื่อเหลือน้อยจนใกล้รอบต่ออายุปกติของผู้ออกใบรับรองนั้น ถ้า `openssl` ไม่มีในเครื่อง
ให้เขียนว่า ตรวจไม่ได้ และแนะนำให้ดูจากไอคอนกุญแจในเบราว์เซอร์แทน

**เสริมด้วย PageSpeed Insights ถ้าผู้ใช้เปิดให้ได้** แปลงตามสีที่เครื่องมือแสดงเอง
เขียวเท่ากับผ่าน ส้มเท่ากับควรดู แดงเท่ากับมีปัญหา ไม่ต้องดูตัวเลข
แต่ถึงไม่มีผล PageSpeed สามการวัดข้างบนก็ต้องมีในรายงานเสมอ

| สัญญาณ | แปลว่า |
|---|---|
| รูปไม่ใช่ WebP หรือ AVIF | รูปหนักกว่าที่ควร |
| `<img>` ไม่ระบุ width height | หน้าเว็บกระตุกตอนโหลด |
| script ใน head ไม่มี defer หรือ async | บล็อกการแสดงผลหน้าแรก |
| script จากโดเมนภายนอกหลายเจ้า | ยิ่งมากยิ่งช้าและคุมไม่ได้ |
| `loading="lazy"` บนรูปใหญ่บนสุด | รูปหลักมาช้า ผิดวิธี |
| รูปแรก ๆ เป็น `src="data:image/..."` ตัวจิ๋ว | รูปจริงถูกสลับด้วย JavaScript ทีหลัง **ห้ามลงว่าผ่าน** ให้ลงเป็น ควรดู เพราะรูปหลักขึ้นช้ากว่าที่ HTML บอก |

## ขั้นที่ 4 มือถือ

Google เก็บข้อมูลด้วยบอทรุ่นมือถือเป็นหลัก **อะไรที่หายบนมือถือ เท่ากับหายจากดัชนี**

| สิ่งที่ดู | ผ่านเมื่อ |
|---|---|
| meta viewport | มีแท็ก |
| ตัวหนังสือ | อ่านออกโดยไม่ต้องซูม |
| ปุ่มและลิงก์ | กดด้วยนิ้วโป้งไม่พลาด ไม่ติดกันจนกดผิด |
| การเลื่อนจอ | ไม่ต้องเลื่อนซ้ายขวาเพื่ออ่าน |
| เนื้อหาสองจอ | ข้อความบนมือถือครบเท่าจอใหญ่ |
| ป๊อปอัป | ไม่บังเนื้อหาทันทีที่เปิดหน้า |

รัน `aiso-technical-lite` ไปแล้วในรอบเดียวกัน ให้อ้างผลมือถือจากไฟล์นั้น แล้วดูเฉพาะข้อที่ขาด

**ขอบเขตของข้อป๊อปอัป** นับเฉพาะสิ่งที่ขึ้นมาบัง **ตอนเปิดหน้าครั้งแรก** คือช่วงระหว่างที่คนกดจากผลค้นหา
จนถึงตอนที่ได้เห็นเนื้อหาที่ตั้งใจมาหา แค่นั้นคือทั้งหมดของข้อนี้
สิ่งที่ขึ้นเพราะผู้ใช้ทำอะไรบางอย่างทีหลัง เช่น เลื่อนจอลงไปแล้วเด้ง หรือเลื่อนเมาส์จะปิดแท็บแล้วเด้ง
**อยู่นอกขอบเขต ห้ามเอามาลงเป็นปัญหาในรายงานนี้** เพราะเป็นการตัดสินใจเรื่อง conversion ไม่ใช่เรื่องการค้นหา
**ประตูยืนยันอายุ และประตูอื่นที่กฎหมายบังคับ ได้รับการยกเว้น** ให้บันทึกว่ามีและได้รับการยกเว้น
ห้ามลงเป็นข้อบกพร่อง

## ขั้นที่ 5 การเข้าดัชนี

| สิ่งที่ดู | ผ่านเมื่อ |
|---|---|
| `/sitemap.xml` | มีไฟล์ เป็น XML ที่อ่านได้ URL ในนั้นเปิดได้ |
| `/robots.txt` | มีบรรทัด Sitemap |
| Grep `noindex` ในไฟล์ HTML ดิบ และในไฟล์ header ที่ดึงมา | หน้าที่อยากติดไม่มี noindex |
| แท็ก canonical | ชี้มาที่ตัวเอง ไม่ชี้ข้ามหน้าโดยไม่ตั้งใจ |
| ลองมีและไม่มี `/` ท้าย ตัวพิมพ์ใหญ่ พารามิเตอร์ | ทุกแบบไปจบที่ URL เดียว |
| เทียบ URL ใน sitemap กับลิงก์ในเมนูและเนื้อหา | ทุกหน้าสำคัญมีทางเดินไปถึง |
| เทียบข้อความที่เห็น กับ HTML ที่ WebFetch ดึงมา | ข้อความหลักอยู่ใน HTML ไม่ใช่รอ JavaScript |

**noindex ที่ค้างคือสาเหตุอันดับหนึ่งของหน้าที่หายจากดัชนี** เจอแล้วให้ขึ้นเป็นข้อแรก
หน้าที่มีแต่โครงเปล่าแล้วเนื้อหาโผล่ทีหลัง นับเป็นมีปัญหา เพราะบอทหลายตัวไม่รันสคริปต์

จำนวนหน้าที่ Google เก็บจริงดูจาก Search Console เท่านั้น
**ห้ามใช้ผลค้น `site:` มาสรุปว่าเป็นจำนวนจริง** เพราะเป็นค่าประมาณที่แกว่งตลอด


**ถ้า sitemap เล็กพอจะไล่ครบได้ในรอบเดียว ให้ไล่ตรวจทุกหน้า ไม่ใช่แค่ 3 หน้าตัวอย่าง**
ในรายงานให้เขียนความครอบคลุมเป็นข้อเท็จจริง เช่น ตรวจครบ 26 หน้าจากทั้งหมด 26 หน้า
หรือ สุ่ม 15 หน้าจากทั้งหมด 120 หน้า ห้ามอธิบายว่าเข้าเกณฑ์อะไรของเรา ลูกค้าไม่ต้องรู้เกณฑ์ภายใน

```bash
grep -o '<loc>[^<]*</loc>' work/{domain}/uploads/sitemap.xml | sed 's/<[^>]*>//g' | while read u; do
  code=$(curl -sS -o /tmp/p.html -w '%{http_code}' -m 20 -A "Mozilla/5.0" "$u")
  robots=$(grep -o '<meta name="robots" content="[^"]*"' /tmp/p.html | head -1)
  canon=$(grep -o '<link rel="canonical" href="[^"]*"' /tmp/p.html | head -1)
  echo "$code | $u | $robots | $canon"
done
```

แล้วหาแถวที่ผิดปกติ คือรหัสไม่ใช่ 200, มี `noindex` บนหน้าที่ควรติด, หรือ canonical ชี้ไปหน้าอื่น
ถ้าใหญ่เกินกว่านั้น ให้สุ่มให้ครอบคลุมทุกประเภทหน้า แล้วเขียนกำกับว่าสุ่มมากี่หน้าจากทั้งหมดกี่หน้า

## ขั้นที่ 5.1 ตรวจก่อนว่าแพลตฟอร์มทำได้ไหม แล้วค่อยโทษหน้าเว็บ

**ต้องทำก่อนจะลงข้อบกพร่องรายหน้าใด ๆ** ถ้าสิ่งที่ขาดไปเป็นสิ่งที่ระบบเว็บ (CMS หรือตัวสร้างหน้า)
ไม่เปิดให้ทำตั้งแต่แรก **นั่นไม่ใช่ข้อบกพร่องของหน้า แต่เป็นข้อจำกัดของแพลตฟอร์ม**
คนละคนแก้ และแก้ครั้งเดียวจบ ไม่ใช่ไล่แก้ทีละหน้าเป็นร้อยเป็นพันหน้า

ไล่ทีละข้อ ลงเป็น **ทำได้** หรือ **ทำไม่ได้** เท่านั้น ไม่มีครึ่ง ๆ กลาง ๆ
ถ้าทำได้เฉพาะบางแม่แบบ ให้ลงว่า ทำไม่ได้ แล้วเขียนกำกับว่าแม่แบบไหนทำได้บ้าง

| ความสามารถ | ทำได้เมื่อ | ถ้าทำไม่ได้ ข้อบกพร่องกลุ่มไหนถูกยุบรวมมาที่นี่ |
|---|---|---|
| ตั้ง title ได้ | ตั้งเป็นแม่แบบต่อหมวดได้ และเขียนทับรายหน้าได้ | title ซ้ำหรือแก้ไม่ได้ ทั้งเว็บ |
| แก้ slug ของ URL ได้ | แก้ได้ | ข้อทักท้วงเรื่องคำใน URL ทั้งเว็บ |
| ตั้ง meta description และ meta robots รายหน้าได้ | ตั้งได้ทั้งสองอย่าง | ทั้งข้อ description และข้อการคุมดัชนี |
| เลือกและแก้แท็กหัวข้อได้ | ไม่ได้ถูกล็อกตายมากับแม่แบบ | ลำดับหัวข้อ H1 ถึง H6 ทั้งเว็บ |
| ตั้งข้อความลิงก์ในเมนูเองได้ | ตั้งได้อิสระจากชื่อหน้าปลายทาง | anchor กว้าง ๆ ในเมนูทั้งเว็บ |
| ซ้อนหมวดหมู่ได้หลายชั้น | ซ้อนได้เกินหนึ่งชั้น | ความลึกและลำดับชั้นของผังเว็บ |
| URL ไม่มีรหัส session และไม่มีพารามิเตอร์ติดตาม | ไม่มีทั้งสองอย่างใน URL ที่บอทเดินได้ | URL งอกเป็นทวีคูณ |
| เด้ง URL รูปแบบแปลกไปหาแบบมาตรฐานให้เอง | เด้งด้วย 301 ครบทุกรูปแบบ | ผลตรวจ URL หลายรูปแบบในขั้นที่ 5 ทั้งชุด |
| สร้าง sitemap ให้ | สร้างให้ | ต้องไปทำ sitemap นอกระบบ |
| หน้ารวมรายการแสดงเป็นเกริ่นย่อ | ไม่ได้ลอกเนื้อหาเต็มมาแสดง | เนื้อหาซ้ำที่เกิดจากหน้ารวมรายการ |
| ลิงก์จากคอมเมนต์และลิงก์โฆษณาใส่ ugc หรือ sponsored ให้เอง | ใส่ให้เป็นค่าตั้งต้น | attribute ของลิงก์ออกในพื้นที่ที่ผู้ใช้เขียนเอง |
| ใส่ noindex กับหน้าคุณค่าต่ำได้ | ใส่ได้ | ทั้งแผนจัดการหน้าคุณค่าต่ำ |

**ข้อไหนดูจากภายนอกไม่ได้ ให้ถามผู้ใช้** ยังไม่ได้คำตอบให้ลงว่า **ตรวจไม่ได้** ห้ามเดาว่าทำได้

รายงานผลครบทุกข้อ **รวมข้อที่ทำได้ด้วย** และข้อที่ทำไม่ได้ต้องบอกว่ามันกลืนข้อบกพร่องรายหน้าไปกี่ข้อ
พร้อมบอกว่าคนที่ต้องแก้เปลี่ยนเป็นใคร (คนที่เปลี่ยนหรือย้ายแพลตฟอร์มได้ ไม่ใช่คนเขียนเนื้อหา)
**ข้อที่ถูกกลืนไปแล้ว ห้ามไปโผล่เป็นแถวรายหน้าซ้ำอีกที่อื่นในรายงาน**
เพราะจะกลายเป็นรายการยาวที่ไม่มีใครทำไหว ซึ่งคือสิ่งที่ขั้นนี้มีไว้กำจัด

## ขั้นที่ 5.2 หน้าไม่ขึ้นดัชนี ต้องบอกให้ได้ว่าเป็นกิ่งไหน

**ห้ามรายงานแค่ตัวเลขว่ามีกี่หน้าไม่ขึ้นดัชนี** ตัวเลขเปล่า ๆ ไม่ใช่ผลตรวจ
เพราะแต่ละสาเหตุแก้คนละแบบ ต้องบอกให้ครบว่า **ใช้ต้นไหน กิ่งไหนติด และหลักฐานคืออะไร**

### ทำก่อนเสมอ หลังเว็บขึ้นใหม่หรือหลังอัปเดตครั้งใหญ่

สองข้อบกพร่องที่ทำลายล้างที่สุดเป็นอุบัติเหตุตอนอัปโหลดทั้งคู่ คือ **noindex ที่ติดมาจากเว็บทดสอบ**
และ **robots.txt ของเว็บทดสอบที่ถูกทับลงไปบนของจริง** ทั้งสองอย่างเอาเว็บทั้งเว็บออกจากดัชนีได้
ทั้งที่คนเปิดดูแล้วเห็นหน้าเว็บปกติดีทุกอย่าง

1. ดึง `robots.txt` ของเว็บจริงมาอ่านให้ครบทั้งไฟล์ สิ่งที่ตามหาคือบรรทัดที่ปิดทั้งเว็บ
2. ดึง meta robots และ header `x-robots-tag` จากหน้าจริง **อย่างน้อยแม่แบบละหนึ่งหน้า**
   ไม่ใช่ทั้งเว็บหน้าเดียว เพราะ noindex ที่ติดมามักอยู่ที่แม่แบบ ไม่ได้อยู่ที่หน้า
3. ทำทันทีหลังอัปเดต ไม่ใช่รอรอบตรวจถัดไป

**เว็บที่เพิ่งเปิดใหม่ไม่มีประวัติทราฟฟิกให้ความผิดพลาดนี้โผล่ออกมา** ไม่มีอันดับตก ไม่มีคนเข้าลด
ไม่มีสัญญาณใน analytics เลย การตรวจข้อนี้จึงเป็นทางเดียวที่จะเจอ และเป็นตอนที่คนข้ามบ่อยที่สุด

### ต้นที่ 1 บอทไม่เคยมาเก็บหน้านี้เลย

ใช้เมื่อยืนยันได้ว่าบอทไม่เคยดึงหน้านี้ **มีกิ่งเดียวที่เป็นสาเหตุ และต้องระบุชื่อกิ่ง**

| กิ่ง | สัญญาณ | ทางแก้ |
|---|---|---|
| robots.txt ปิดไว้ | มีบรรทัดใน robots.txt ที่ตรงกับ path นี้ สำหรับบอทตัวนั้น | เอาออกหรือทำให้แคบลง แล้วดึง robots.txt ของจริงมาดูซ้ำว่าไม่ตรงแล้ว ห้ามเชื่อไฟล์ที่ดึงมารอบก่อน |
| มี noindex | meta robots หรือ header มี noindex ติดอยู่ | เอาออกทั้งสองที่ · **noindex ที่ค้างนาน ๆ ทำให้บอทเลิกมาที่หน้านั้นไปเลย และเมื่อเลิกมา ลิงก์ที่หน้านั้นชี้ออกไปก็ถูกนับว่าไม่ส่งต่อ** คือเสียทั้งตัวหน้า และเสียลิงก์ที่มันเคยส่งให้หน้าอื่นด้วย |
| ไม่มีลิงก์ไปถึงเลย | ไม่มี href จากหน้าไหนชี้มา และไม่อยู่ใน sitemap | เพิ่มลิงก์จริงจากหน้าที่บอทเดินถึงอย่างน้อยหนึ่งเส้น และใส่ใน sitemap ด้วย · อยู่ใน sitemap อย่างเดียวเป็นทางที่อ่อนกว่าลิงก์ ต้องมีทั้งคู่ |
| อยู่หลังการล็อกอินหรือหลังกดส่งฟอร์ม | เข้าถึงได้ต่อเมื่อล็อกอิน หรือต่อเมื่อกดส่งฟอร์ม | บอทไม่ล็อกอินและไม่กดส่งฟอร์ม ต้องเปิด URL ที่เทียบเท่าให้เดินถึงได้ หรือยอมรับว่าตั้งใจให้เป็นความลับ |
| URL มีรหัส session หรือรหัสติดตาม | เข้าทีไรได้ URL ใหม่ทุกที ทั้งที่เนื้อหาเดิม บอทเลยเจอ URL คล้ายกันไม่รู้จบ | เอารหัสออกจาก URL ที่บอทเดินได้ทั้งหมด เก็บสถานะไว้นอก URL |
| ไม่มีน้ำหนักพอให้บอทสนใจ | เดินถึงได้ ไม่มีอะไรผิดเชิงเทคนิค แต่ไม่มีใครลิงก์ถึงอย่างมีน้ำหนัก | ยกความเด่นขึ้น ลิงก์จากหน้าที่บอทมาบ่อยและอยู่ตื้นกว่า · เป็นกิ่งเดียวที่ทางแก้ไม่ใช่การแก้เชิงเทคนิค |

พร้อมกับชื่อกิ่ง ให้ระบุด้วยว่าที่บอทพลาดหน้านี้เป็นเพราะอะไรใน 4 อย่างนี้

1. **ไม่เคยถูกค้นพบ** ไม่เคยมีทางไปถึง ไม่มีลิงก์ ไม่มีใน sitemap ไม่มีใครส่งต่อ บอทพลาดสิ่งที่ไม่เคยมีใครชี้ให้ดูไม่ได้
2. **อยู่ลึกเกินไป** มีทางอยู่ แต่ต้องเดินหลายชั้นเกินกว่าที่บอทจะไล่ลงมาถึง
3. **เคยเก็บแล้วและเลิกสนใจ** ส่งซ้ำเฉย ๆ มักไม่ช่วย ต้องเปลี่ยนตัวหน้า หรือเปลี่ยนความเด่นของลิงก์ที่ชี้มา
4. **โควตาการเก็บหมดก่อนจะถึงคิว** เกิดจากสองอย่างคือ เซิร์ฟเวอร์มีปัญหาช่วงนั้น (ตอบช้าหรือตอบ error กินโควตาไปโดยไม่ได้เนื้อหากลับมา) และมี URL จำนวนมากที่เนื้อหาเหมือนกัน (โควตาหมดไปกับการเก็บของซ้ำ)

### ต้นที่ 2 บอทเก็บไปแล้ว แต่หน้ายังไม่อยู่ในดัชนี

**เป็นคนละต้นกับต้นที่ 1 ห้ามรันสองต้นพร้อมกัน**

| กิ่ง | สัญญาณ | ทางแก้ |
|---|---|---|
| มี noindex | meta robots หรือ header ในคำตอบที่บอทได้รับ มี noindex | เอาออกทั้งสองที่ แล้วขอให้เก็บใหม่ |
| เนื้อหาไม่พอ หรือคุณภาพไม่พอ | เก็บไปแล้ว แต่ตัดสินว่าไม่คุ้มจะเอาเข้าดัชนี | **ยืนยันด้วยการอ่านหน้านั้น ห้ามตัดสินจากขนาดไฟล์เป็นไบต์** เพราะไบต์รวมแม่แบบ เมนู และสคริปต์ ซึ่งไม่บอกอะไรเลยว่าหน้ามีเนื้อจริงแค่ไหน · ทางแก้คือเติมเนื้อที่ยังไม่มี หรือยุบรวมเข้ากับหน้าที่มีอยู่แล้ว |
| ไม่มีลิงก์ทั้งจากในเว็บและนอกเว็บ | ไม่มีลิงก์ภายในและไม่มีลิงก์ภายนอกชี้มาเลย เคยเดินถึงได้ครั้งหนึ่งเช่นจาก sitemap แต่ไม่มีใครการันตีมัน | เพิ่มลิงก์ภายในจากหน้าที่เกี่ยวข้อง · เงื่อนไขคือขาด**ทั้งสองแบบ** มีอย่างใดอย่างหนึ่งก็เปลี่ยนกิ่งแล้ว |
| มีบทลงโทษที่ตั้งด้วยคน | มีรายการบทลงโทษบันทึกไว้กับเว็บหรือกับส่วนนั้น | **ห้ามวินิจฉัยหรือแก้ในสกิลนี้** บันทึกไว้ แล้วบอกผู้ใช้ให้ไปเปิด Search Console หัวข้อ Manual actions ดูเอง |
| ถูกกดซ่อนด้วยเครื่องมือลบเนื้อหาเก่า | มีการส่ง URL เข้าเครื่องมือลบเนื้อหาที่ล้าสมัย | เครื่องมือนั้นไม่เคยลบอะไรออกจากดัชนี มันแค่ซ่อนผลลัพธ์ และการซ่อนหมดอายุตามที่ Google ประกาศไว้ (ราว 180 วัน) แล้ว URL จะโผล่กลับมาถ้าตัวหน้าไม่ได้เปลี่ยน · ถ้าตั้งใจซ่อน ให้วางแผนแก้ของจริงก่อนหมดอายุ ถ้าไม่ได้ตั้งใจ ให้ถอนคำขอ |

### สัญญาณจาก analytics ใช้ตั้งรายชื่อผู้ต้องสงสัย ไม่ใช่คำตัดสิน

- **หน้าที่มีคนเข้า แต่ไม่มีใครเข้ามาจากการค้นหาเลย** เป็นผู้ต้องสงสัยว่าไม่อยู่ในดัชนี
  แต่หน้าที่อยู่ในดัชนีแล้วไม่เคยติดอันดับก็ให้ภาพแบบเดียวกัน จึงเป็นแค่รายชื่อ ไม่ใช่ข้อสรุป
- **จำนวนหน้าในดัชนีเทียบกับจำนวนหน้าที่เว็บมีจริง ต้องดูเป็นแนวโน้ม** ค่าครั้งเดียวไม่พิสูจน์อะไร
  ต้องต่ำต่อเนื่องหรือกำลังลดลง ถึงจะเป็นสัญญาณ
- **แยก sitemap ตามกลุ่มเนื้อหา** แล้วรายงานความครอบคลุมทีละไฟล์ จะรู้ว่าส่วนไหนของเว็บกำลังพัง
  แทนที่จะได้ตัวเลขรวมของทั้งเว็บที่กลบปัญหาไว้

ทุกข้อในหัวข้อนี้ต้องเอาไปยืนยันกับต้นที่ 1 หรือต้นที่ 2 ก่อน ถึงจะกลายเป็นข้อค้นพบได้

## ขั้นที่ 5.3 canonical ต้องนับ ไม่ใช่อ่านตัวแรกแล้วจบ

**นับจำนวนแท็ก canonical บนหน้านั้นเสมอ ห้ามอ่านตัวแรกแล้วหยุด**
เพราะตัวแยกที่คืนค่าแรกที่เจอ จะรายงาน canonical ที่จริง ๆ แล้วไม่มีผลบังคับ

| รูปแบบที่หักล้างกันเอง | เกิดอะไรขึ้น |
|---|---|
| หน้าเดียวมี canonical สองอัน ชี้คนละที่ | หักล้างกัน ไม่มีอันไหนมีผล |
| หน้า A ชี้ไปหน้า B และหน้า B ชี้กลับมาหน้า A | หักล้างกันทั้งคู่ ไม่มี URL ไหนถูกยุบรวม |

เจอรูปแบบไหนก็ตาม **ผลต้องเขียนว่า `canonical ไม่มีผลบังคับ` ห้ามเขียนว่า `มี canonical`**
เพราะคำว่ามีจะปิดข้อตรวจนี้ทิ้งไป แล้วเรื่องเนื้อหาซ้ำก็ไม่ถูกแก้

**canonical ส่งมาทาง response header ได้ด้วย** ในหัวข้อ `Link`
และนั่นคือ **ทางเดียวที่ทำ canonical ให้ไฟล์ PDF ได้** เพราะ PDF ไม่มี `<head>` ให้ใส่แท็ก
ตัวแยกที่ดูแต่ `<head>` จะพลาดทั้งหมด แล้วรายงานว่าหน้านั้นไม่มี canonical
**ต้องอ่าน header ด้วยทุกครั้งก่อนเขียนว่าไม่มี canonical** และต้องบอกด้วยว่าเจอมาจากช่องทางไหน

```bash
grep -o -i '<link[^>]*rel="canonical"[^>]*>' work/{domain}/uploads/home.html | wc -l
grep -i '^link:' work/{domain}/uploads/home-headers.txt
```

## ขั้นที่ 5.4 sitemap สะอาดพอจะใช้สั่งงานบอทไหม

sitemap คือรายการ URL ที่เว็บ **อยากให้เก็บและอยากให้ติดดัชนี** อะไรที่ขัดกับเจตนานั้นต้องเอาออก

| ต้องไม่มีใน sitemap | เพราะ |
|---|---|
| URL ที่ไม่ตอบ 200 | ขัดกับเจตนาของไฟล์ |
| URL ที่ canonical ชี้ไปที่อื่น | ตัวเว็บเองบอกว่าอยากให้เก็บอันอื่นแทน |
| URL ที่มี noindex | ตัวเว็บเองบอกว่าไม่อยากให้ติดดัชนี |
| URL ที่เด้งไปที่อื่น | ปลายทางต่างหากที่ควรอยู่ในรายการ |
| URL ที่ robots.txt ปิดไว้ | สั่งสองอย่างสวนทางกัน |

**เจอกลุ่มไหนก็ตาม ให้ลงเป็นข้อบกพร่องของไฟล์ ไม่ใช่ของหน้า**

- **ไฟล์เดียวต้องไม่เกิน 50 MB** ตามข้อกำหนดของ sitemap protocol ที่ประกาศไว้เป็นสาธารณะ
  เกินกว่านั้นให้แตกเป็นหลายไฟล์ แล้วทำไฟล์ดัชนีชี้ไปหา
- **`changefreq` ถูกเมินไปแล้ว เลิกรายงานทั้งหมด** ห้ามตรวจ ห้ามลงว่าขาด และห้ามแนะนำให้ใส่หรือให้แก้
  แถว changefreq ในรายงานคือการสร้างงานที่ไม่มีผลอะไรเลย
- **sitemap เฉพาะทางสามแบบ คือ video, image และ news ให้รายงานว่า มี / ไม่มี / ไม่เกี่ยวกับเว็บนี้**
  คำว่า ไม่เกี่ยวกับเว็บนี้ เป็นคำตัดสินจริง ๆ ต้องใช้เมื่อเว็บไม่ได้ผลิตเนื้อหาแบบนั้นเลย
  การลงว่าเว็บที่ไม่มีข่าวเลย ขาด news sitemap คือข้อค้นพบปลอม

## ขั้นที่ 5.5 กับดักบอท เนื้อหาซ้ำ และ PDF

### กับดักบอท ให้รายงานตัวผลิต ไม่ใช่ URL ตัวอย่าง

สัญญาณคือ **จำนวน URL ที่บอทเดินได้มากกว่าจำนวนเนื้อหาจริงแบบคนละชั้น** ไม่ใช่มากกว่านิดหน่อย
เจอช่องว่างแบบนั้นแล้วให้ไล่หาว่าอะไรเป็นตัวผลิต

| ตัวผลิต | กลไก |
|---|---|
| การเด้งที่วนกลับมาที่เดิม | เด้งไปแล้ววนกลับมาที่ URL ที่อยู่ในสายเดิม บอทเดินวนไม่จบ |
| ปฏิทินหรือการเดินตามวันที่ | ลิงก์เดือนหน้าปีหน้าที่กดต่อได้ไม่สิ้นสุด ผลิตหน้าว่างไม่จำกัด |
| หน้าสุดท้ายของ pagination ที่ยังมีปุ่มถัดไป | ชุดหน้าไม่มีวันจบ |
| ตัวกรองที่จับคู่กันได้ทุกแบบ | ทุกการผสมตัวกรองได้ URL ใหม่ ชุด URL โตแบบทวีคูณเทียบกับเนื้อหาที่มีอยู่นิดเดียว |

**รายงานชื่อตัวผลิต กลไกของมัน และขนาดของชุดที่กระทบ ห้ามลงรายการ URL ตัวอย่าง**
เพราะการลง URL ตัวอย่างจะชวนให้ไปไล่ลบทีละ URL ซึ่งตัวผลิตจะสร้างกลับมาใหม่ทันที

### เนื้อหาซ้ำ ใช้สามวิธีที่ต้นทุนต่ำ

1. **หยิบประโยคที่มีเอกลักษณ์มาค้นแบบครอบเครื่องหมายคำพูด** ค้นสองรอบ
   รอบแรกจำกัดในโดเมนตัวเองเพื่อหาการซ้ำกันภายในเว็บ รอบสองไม่จำกัดเพื่อหาข้อความเดียวกันบนเว็บอื่น
   **ต้องทำทั้งสองรอบ** ทำรอบเดียวได้คำตอบแค่ครึ่งเดียว
2. **จับกลุ่มหน้าที่ title กับหัวข้อเหมือนกันเป๊ะ** ได้แค่ **รายชื่อผู้ต้องสงสัย**
   title ซ้ำเป็นอาการ ไม่ใช่หลักฐานว่าเนื้อในซ้ำ ต้องเปิดเทียบเนื้อหาจริงทีละคู่
3. **ทำ hash ของเนื้อหน้าแล้วจับกลุ่มที่ตรงกัน** จับของที่เหมือนกันทุกไบต์ได้ถูกและเร็ว
   และพลาดทุกอย่างที่ต่างกันแม้แต่ตัวอักษรเดียว

**หน้าในชุด pagination ได้รับการยกเว้น** หน้าย่อยของชุดเดียวกันใช้แม่แบบและข้อความกรอบเดียวกันโดยชอบธรรม
ห้ามรายงานว่าเป็นเนื้อหาซ้ำ

### PDF

นับ PDF เป็น **สัดส่วนของสิ่งที่บอทเดินเจอทั้งหมด ไม่ใช่จำนวนดิบ**
จำนวนดิบไม่มีความหมายถ้าไม่รู้ว่าอยู่ในกองใหญ่แค่ไหน

**PDF ที่บรรจุข้อมูลที่ธุรกิจอยากให้คนหาเจอ ต้องมีหน้า HTML ที่เทียบเท่า**
ตัว PDF อยู่ต่อได้ในฐานะไฟล์ให้ดาวน์โหลด แต่หน้า HTML คือสิ่งที่ถูกเก็บ ถูกลิงก์ ถูกอัปเดต และถูกหยิบไปอ้าง
รายงานเป็นสัดส่วน ระบุว่าส่วนไหนของเว็บพึ่ง PDF และ PDF ตัวไหนยังไม่มี HTML คู่กัน

## ขั้นที่ 6 เขียนรายงาน

ชื่อไฟล์ต้องเป็นแบบนี้ **เหมือนกันเป๊ะ** กับที่ประกาศไว้ใน `agent.json`

```
work/{domain}/(00-baseline|01-current)/{domain}_technical-audit_{YYYY-MM-DD}.md
```

1. **ขอบเขตการตรวจ** กี่หน้า หน้าไหน อะไรที่ยังไม่ได้ดู
2. **สรุปหนึ่งย่อหน้า** ว่ามีอะไรขวางอยู่
3. **ตารางรวม** คอลัมน์ ด้าน / ระดับ / เรื่องที่ต้องแก้ ครบทุกด้านที่ตรวจ
4. **มีปัญหา** คอลัมน์ เรื่อง / เจอที่หน้าไหน / แก้ยังไง / ใครแก้ได้
5. **ควรดู** และ **ตรวจไม่ได้** ตารางแบบเดียวกัน ของตรวจไม่ได้ให้ระบุว่าขาดอะไร
6. **ข้อจำกัดของแพลตฟอร์ม** ผลของขั้นที่ 5.1 ครบทุกข้อ รวมข้อที่ทำได้ พร้อมจำนวนข้อบกพร่องรายหน้าที่ถูกกลืนเข้ามา
7. **สามอย่างที่ควรแก้ก่อน** เรียงตามผลกระทบ พร้อมเหตุผลสั้น ๆ
8. **ส่งต่อให้สกิลไหน**

## การ์ด Tier 1 ของสกิลนี้

จบงานทุกครั้งด้วยการ์ดสรุปตามชั้นแสดงผล (`so-present-lite`): โหมด `audit` `dimensions` คือจำนวนข้อที่ผ่านต่อจำนวนข้อที่ตรวจในแต่ละหมวด, `key_risk` คือข้อที่กั้นการ crawl หรือ index ที่กระทบหน้ามากที่สุด, `actions` คือ 4 ข้อแรกของรายการแก้, `transparency.could_not_verify` คือหมวดที่ตรวจไม่ได้พร้อมเหตุ

แล้วปิดด้วยบรรทัดส่งต่อไปยังไฟล์ผลลัพธ์ฉบับเต็ม ซึ่งต้องครบและไม่ถูกย่อ

## การวางไฟล์ผลลัพธ์

สกิลนี้อยู่ในชุดที่ใช้โครงโฟลเดอร์ของสกิล `new-workspace-lite`

1. ผลลัพธ์ทุกไฟล์อยู่ใต้ `work/{domain}/`
2. ถ้า `work/{domain}/00-baseline/` ยังไม่มีไฟล์หัวข้อเดียวกัน ให้เขียนลง `00-baseline/` ถ้ามีแล้ว ให้เขียนลง `01-current/`
3. เขียนเสร็จ ให้เพิ่มบรรทัดลงตารางใน `work/{domain}/CHANGELOG.md` ว่าวันที่ รันสกิลอะไร ได้ไฟล์อะไร
4. ถ้ายังไม่มี `work/{domain}/` ให้แนะนำผู้ใช้รันสกิล `new-workspace-lite` ก่อน ห้ามสร้างโครงเองแบบอื่น

## ข้อจำกัดที่ต้องบอกผู้ใช้ทุกครั้ง

**ถ้าดึง HTML ดิบในขั้นที่ 0 ไม่สำเร็จ** จะตรวจ mixed content, meta robots และ JSON-LD ไม่ได้
เพราะ WebFetch ตัดแอตทริบิวต์และแท็กใน head ทิ้งไปตอนแปลงเป็นข้อความ

ในรายงานต้องเขียนกำกับไว้ว่า **ตรวจได้เท่าที่เห็นจากเนื้อหาที่ดึงมา ไม่ได้ดูซอร์สจริง**
และแนะนำให้ผู้ใช้เปิด View Source หรือ DevTools ดูเองอีกรอบสำหรับสองหัวข้อนี้

ห้ามสรุปว่า ผ่าน ถ้าไม่ได้เห็นซอร์สจริง ให้ใช้ผลว่า **ตรวจไม่ได้** แทน

### header แกว่งตามชั้นแคชได้ ต้องเทียบก่อนตัดสิน

- บางเว็บตอบ header จากแคช CDN ไม่เหมือนจากเซิร์ฟเวอร์ต้นทาง ก่อนตัดสิน header ความปลอดภัยหรือแคชใด ๆ
  ให้ดึงอย่างน้อย 2 ครั้งแล้วเทียบตัวบอกชั้นแคช เช่น `cf-cache-status`, `x-cache`, `age`
  ถ้า header อย่าง `strict-transport-security` โผล่เฉพาะรอบที่หลุดไปต้นทาง
  ให้ลงผลว่า **ไม่นิ่งที่ชั้นแคช ผู้ใช้จริงส่วนใหญ่ไม่ได้รับ** ห้ามลงว่าผ่าน
- ตอนตรวจการบีบอัด ต้องส่ง `Accept-Encoding` แบบเบราว์เซอร์ คือใช้ `curl --compressed`
  เพราะ curl เปล่า ๆ ได้ของไม่บีบอัดโดยดีไซน์ การสรุปว่าไม่มีการบีบอัดจากมันคือการสร้างงานแก้ปลอม
- script ที่บล็อกการแสดงผลนับเฉพาะที่อยู่**ใน `<head>`** เท่านั้น หา `</head>` ก่อนแล้วนับเฉพาะก่อนหน้านั้น
  script ท้าย `<body>` ไม่บล็อก อย่านับรวมแล้วรายงานเกินจริง
- ก่อนนับจำนวนคำของหน้า ต้องตัดเนื้อใน `<script>` และ `<style>` ทิ้งก่อน
  ไม่งั้นโค้ดจะถูกนับเป็นคำ แล้วตัวเลขเพี้ยนได้เป็นสิบเท่า

## กฎ


- **ถ้าดึงข้อมูลไม่สำเร็จ ให้เขียนว่า `ตรวจไม่ได้` ห้ามเขียนว่า `ไม่มี`** สองคำนี้คนละความหมาย ถ้าเขียนผิดผู้ใช้จะสรุปกลับด้าน
- **ทำได้บางส่วนต้องส่งส่วนนั้นเสมอ** ห้ามส่งตารางที่ทุกช่องว่าง และห้ามปฏิเสธทั้งงานเพราะขาดข้อมูลบางอย่าง ให้ติดป้ายว่าข้อไหนยืนยันแล้ว ข้อไหนต้องยืนยันเพิ่ม · การใช้ข้อจำกัดเป็นข้ออ้างไม่ส่งงาน ไม่ใช่ความซื่อสัตย์
- **ห้ามให้คะแนนรวม ห้ามคิดเปอร์เซ็นต์ ห้ามให้เกรด** ใช้สี่ระดับเท่านั้น
- **ห้ามเดาตัวเลขความเร็ว และห้ามตั้งเกณฑ์เอง** ไม่มีผลจากเครื่องมือให้เขียนว่ายังไม่ได้วัด
- **ห้ามเขียนรายชื่อ AI crawler ในสกิลนี้** ส่งต่อไปที่ `aiso-crawlers-lite`
- **ห้ามรายงานข้อที่ไม่ได้ตรวจว่าผ่าน** ไม่ได้ดูให้ลงเป็นตรวจไม่ได้
- **ห้ามรายงานปัญหาการเข้าดัชนีเป็นตัวเลขเปล่า ๆ** ต้องบอกว่าใช้ต้นไหน กิ่งไหนติด
  ถ้าเป็นต้นที่ 1 ต้องบอกด้วยว่าบอทพลาดเพราะสาเหตุไหนใน 4 อย่าง และต้องมีหลักฐานที่ยกมาจากคำตอบจริง
- **ข้อบกพร่องที่ถูกยุบเป็นข้อจำกัดของแพลตฟอร์มแล้ว ห้ามไปโผล่เป็นแถวรายหน้าซ้ำอีก** ในรายงานเดียวกัน
- **ห้ามสรุปว่าทั้งเว็บเป็นแบบนี้** ถ้าตรวจแค่บางหน้า
- **ห้ามแก้ไฟล์บนเว็บจริง** สกิลนี้อ่านและเขียนรายงานเท่านั้น
- ถ้าข้อมูลไม่พอให้เขียนตรง ๆ ว่าไม่พอ และบอกว่าต้องใช้อะไรเพิ่ม
